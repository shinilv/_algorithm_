1. 第一遍只看题目，先用 60-90 秒说明项目目标、个人贡献和核心调用链，再看参考答案补缺口。

回答项目题时，可采用下面的四步结构：

# 一、基于 C++11 重构 Muduo 网络库（1-12）

## 1. `[S]` 请介绍一下这个项目，你为什么要重写 Muduo？

### 参考答案

这个项目是我为了系统理解 Linux 高并发网络编程，参考 Muduo 源码及其典型设计，用 C++11 重新实现的一个学习版核心网络库。我没有把它描述成从零发明的新框架，也没有完整复刻官方 Muduo，而是围绕 TCP 服务端最关键的链路，实现了 `EventLoop`、`Channel`、`Poller`、`EPollPoller`、`Acceptor`、`TcpServer`、`TcpConnection`、`Buffer` 以及线程池等模块。

技术上，我用 epoll LT、非阻塞 I/O 和 Reactor 模型完成事件驱动；用 one loop per thread 组织主从 Reactor；用 `eventfd` 和任务队列处理跨线程唤醒；再用 `unique_ptr`、`shared_ptr`、`weak_ptr`、RAII 和回调管理资源与连接生命周期。这个项目对我最大的价值不是“造了一个比官方更强的库”，而是把连接建立、事件分发、数据收发、跨线程调度和连接销毁整条链路真正串了起来，也让我能从源码层面解释其中的设计取舍和现有不足。

### 答题要点

- 诚实定位：参考 Muduo 源码重写的学习版核心子集，不宣称从零原创完整框架。
- 核心模块：Reactor、epoll、TCP 连接、缓冲区、线程池和生命周期管理。
- C++11 实践：线程、原子变量、函数对象、智能指针、互斥锁和条件变量。
- 项目价值：掌握完整网络事件链路，并能分析源码缺陷和改进方向。

### 面试官追问

**追问 1：既然是参考源码重写，你自己的工作体现在哪里？**  
**答：** 我的工作主要是按依赖关系拆解模块，自己完成接口衔接、编码、构建和 Echo 服务验证，并逐段跟踪建连、读写和销毁流程。我会明确哪些设计来自 Muduo，例如 `Channel` 抽象、one loop per thread 和 `eventfd` 唤醒，不会把成熟框架的设计包装成个人原创。

**追问 2：它和完整的 Muduo 相比还缺少什么？**  
**答：** 当前项目聚焦 TCP 服务端核心链路，缺少定时器体系、`TcpClient`、连接器、异步日志、HTTP 等模块，也缺少官方库长期积累的异常处理、测试和工程化细节，所以更准确的叫法是“重写 Muduo 核心模块”。

## 2. `[S]` 这个项目中的 Reactor 模型和一次完整请求链路是怎样的？

### 参考答案

我的实现属于同步非阻塞 I/O 加 I/O 多路复用的 Reactor，不是 Linux AIO 或 io_uring 意义上的真正异步 I/O。程序启动后，主线程创建 base `EventLoop`，`TcpServer` 内部的 `Acceptor` 创建、绑定并监听非阻塞 socket；如果配置了工作线程，`EventLoopThreadPool` 会为每个工作线程创建独立的 sub `EventLoop`。

当 listenfd 就绪时，base loop 的 epoll 返回对应 `Channel`，再回调 `Acceptor::handleRead`，通过 `accept4` 得到非阻塞 connfd。`TcpServer` 轮询选择一个 sub loop，创建 `TcpConnection` 并把建立连接任务投递过去。之后该连接的读写事件都由所属 sub loop 处理：读事件进入 `Buffer` 后调用业务回调，业务调用 `send` 返回响应；写不完的数据进入输出缓冲区并等待 EPOLLOUT。对端关闭后，连接先从主循环的连接表移除，再到所属子循环注销 `Channel`，最后由 RAII 释放 socket。

### 答题要点

- Reactor 本质：事件到达后分发回调，实际 `read/write` 仍由应用线程同步执行。
- 主链路：epoll → Channel → Acceptor/TcpConnection → 业务回调。
- 主 Reactor 接收连接，子 Reactor 负责已连接 socket 的读写。
- 连接销毁同样跨主、子循环协调，不能直接在任意线程释放。

### 面试官追问

**追问 1：Reactor 和 Proactor 的核心区别是什么？**  
**答：** Reactor 通知“fd 已经可以读写”，应用收到通知后自己调用 `read/write`；Proactor 通知的是“异步 I/O 操作已经完成”，数据搬运由内核或异步设施完成。我的项目是 Reactor。

**追问 2：为什么 epoll 必须配合非阻塞 socket？**  
**答：** 就绪只代表当前时刻某个操作大概率不会阻塞，不保证一次调用能完成全部工作。如果 fd 是阻塞的，单个连接上的慢操作可能卡住整个 EventLoop，使同一循环管理的其他连接都得不到处理。

## 3. `[S]` `EventLoop`、`Channel`、`Poller` 和 `EPollPoller` 分别负责什么？

### 参考答案

我把这四个类理解为 Reactor 的四个层次。`EventLoop` 是事件循环和线程归属的核心，它不断调用 `Poller::poll`，遍历活跃 `Channel`，最后执行跨线程投递过来的任务。`Channel` 不拥有 fd，它只是 fd 的事件代理，保存感兴趣的 `events_`、实际发生的 `revents_`，以及读、写、关闭和错误回调。

`Poller` 是 I/O 多路复用的抽象接口，定义 `poll`、更新和移除 `Channel`；当前真正实现的是 `EPollPoller`。它维护 fd 到 `Channel*` 的映射，并用 `kNew`、`kAdded`、`kDeleted` 三种状态决定执行 `EPOLL_CTL_ADD`、`MOD` 还是 `DEL`。注册时把 `Channel*` 放进 `epoll_event.data.ptr`，所以 `epoll_wait` 返回后可以直接找到事件代理，再由 EventLoop 完成回调分发。

### 答题要点

- `EventLoop`：驱动循环、分发活跃事件、执行待处理任务。
- `Channel`：封装 fd 的事件与回调，但不负责关闭 fd。
- `Poller`：屏蔽具体 I/O 多路复用实现；`EPollPoller` 封装 epoll。
- 三态管理避免重复 ADD，并正确处理暂时取消监听和彻底移除。

### 面试官追问

**追问 1：`events_` 和 `revents_` 有什么区别？**  
**答：** `events_` 是应用希望监听的事件集合，例如 EPOLLIN、EPOLLOUT；`revents_` 是 `epoll_wait` 本次实际返回的事件。前者用于注册和修改，后者用于决定执行哪个回调。

**追问 2：为什么 `Channel` 不直接负责关闭 fd？**  
**答：** `Channel` 只是事件代理，同一个 fd 的资源所有权属于更上层的 `Socket` 或 `TcpConnection`。如果 Channel 也关闭 fd，会让事件管理和资源所有权混在一起，容易出现重复关闭。

## 4. `[S]` 一个 `TcpConnection` 从建立到销毁的生命周期是怎样管理的？

### 参考答案

新连接由 base loop 中的 `Acceptor` 接收，`TcpServer::newConnection` 为它选择一个 ioLoop，创建 `TcpConnection`，并把 `shared_ptr` 保存到只由 base loop 管理的 `connections_` 中。随后把 `connectEstablished` 投递到 ioLoop，在连接所属线程里把状态改为 connected，通过 `Channel::tie` 绑定弱引用，再注册读事件并执行连接回调。

关闭时可能是读到 0 或收到关闭事件。`handleClose` 先把状态设为 disconnected，并取消 Channel 的全部关注事件，然后通过关闭回调把 `removeConnection` 投递到 base loop。base loop 从 `connections_` 删除连接，再把 `connectDestroyed` 投递回 ioLoop，由所属线程从 epoll 中移除 Channel。这样能保证连接表只在主循环修改，Channel 只在所属 I/O 线程修改；最后一个 `shared_ptr` 释放后，`Socket` 析构关闭 fd。当前源码仍有部分裸 `this` 捕获，所以我会把它看成已有设计目标，而不是宣称生命周期已经完全无漏洞。

### 答题要点

- `connections_` 中的 `shared_ptr` 是连接存活的主要所有权。
- 建立和注销 Channel 都在连接所属 ioLoop 内执行。
- 关闭流程跨 ioLoop、baseLoop、ioLoop 三个阶段完成。
- `Channel::tie` 在事件回调期间临时提升弱引用，降低对象提前销毁风险。

### 面试官追问

**追问 1：为什么不能在 `handleClose` 中直接删除连接对象？**  
**答：** `handleClose` 正在执行该对象和 Channel 的回调，立即删除可能让当前调用栈或活跃事件列表访问悬空对象；同时连接表属于 base loop。通过任务投递分阶段销毁可以维持线程归属和回调期生命周期。

**追问 2：为什么 `tie` 用 `weak_ptr`，不用 `shared_ptr`？**  
**答：** Channel 如果长期持有 TcpConnection 的 `shared_ptr`，而 TcpConnection 又拥有 Channel，就可能形成循环引用。弱引用不增加长期引用计数，只在事件处理开始时提升为临时 `shared_ptr` 保护本次回调。

## 5. `[S]` one loop per thread 是如何实现的，它为什么能降低锁竞争？

### 参考答案

项目中的 `EventLoopThread` 封装一个工作线程，线程入口函数在自己的栈上创建一个 `EventLoop`，因此一个线程只运行一个事件循环。主线程通过互斥锁和条件变量等待这个 EventLoop 初始化完成，再把指针交给 `EventLoopThreadPool` 保存。`TcpServer` 接收到新连接后，用 round-robin 从 `loops_` 中选择一个 ioLoop；没有配置工作线程时，就退化为全部由 base loop 处理。

降低竞争的关键不是“线程多”，而是线程归属。一个连接一旦分配给某个 ioLoop，它的 Channel、输入缓冲区和输出缓冲区原则上都只由该线程访问，因此热路径不需要给每个读写操作加锁。跨线程操作不直接修改连接内部状态，而是通过 `runInLoop/queueInLoop` 投递给所属线程。这个轮询只按连接数分配，不感知连接实际负载，所以它能做到大致均匀，但不能保证真正的负载最优。

### 答题要点

- 每个 `EventLoopThread` 在线程栈上创建一个 EventLoop。
- 新连接按 round-robin 固定分配给某个 ioLoop。
- 线程归属让 Channel 和 Buffer 的常规访问避免加锁。
- 轮询均衡的是连接数，不是 CPU、流量或任务耗时。

### 面试官追问

**追问 1：一个连接建立后可以迁移到其他 EventLoop 吗？**  
**答：** 当前实现没有连接迁移机制。Channel 从注册开始就绑定 owner loop，迁移需要安全暂停事件、转移缓冲区和状态、重新注册 epoll，复杂度和风险都较高。

**追问 2：如果某个连接非常繁忙，轮询会有什么问题？**  
**答：** 某个 sub loop 可能因为少数重连接过载，而其他 loop 较空闲。生产实现可以采集各 loop 的连接数、待发送字节和任务耗时，再做最小负载选择，但也要权衡统计和迁移成本。

## 6. `[S]` 为什么使用 `eventfd` 做跨线程唤醒，任务队列又是怎样保证线程安全的？

### 参考答案

当其他线程要让某个 EventLoop 执行任务时，我不会直接跨线程操作它的 Channel，而是把 `std::function<void()>` 放入 `pendingFunctors_`。这个 vector 可能被多个线程同时写，所以入队时用 mutex 保护；随后向非阻塞 `eventfd` 写入一个 64 位整数，使正在 `epoll_wait` 中阻塞的 loop 立刻收到可读事件。

EventLoop 处理 wakeup Channel 时读取 eventfd，把计数清走，然后在 `doPendingFunctors` 中先用一个局部 vector 与共享队列 `swap`，快速释放锁，再逐个执行回调。`queueInLoop` 在调用者不是所属线程时一定唤醒；如果 loop 正在执行一批 pending functor，又有新任务入队，也要唤醒，避免新任务因为本轮已经完成 swap 而在下一次 epoll 中等待最多十秒。eventfd 的计数语义还能合并多次通知，任务本身仍以队列为准。

### 答题要点

- mutex 保护任务容器，eventfd 负责打断 `epoll_wait`，二者职责不同。
- eventfd 是可被 epoll 监听的轻量级 64 位计数器。
- `swap` 缩短锁持有时间，也允许回调中继续投递任务。
- `callingPendingFunctors_` 解决执行回调期间再次入队的延迟问题。

### 面试官追问

**追问 1：多次调用 `wakeup` 会不会丢任务？**  
**答：** eventfd 会累计计数，一次读取可以合并多次唤醒；即使通知被合并，真正的任务仍完整保存在受锁保护的队列里，所以正确性依赖任务队列，不依赖“一次通知对应一个任务”。

**追问 2：为什么不用条件变量唤醒 EventLoop？**  
**答：** 条件变量不能直接成为 epoll 监听对象，使用它通常还需要额外等待线程或改变事件循环结构。eventfd 本身就是 fd，可以和网络事件统一进入同一个 epoll 分发流程。

## 7. `[S]` `Buffer` 的读写下标和 `readv` 双缓冲设计有什么作用？

### 参考答案

`Buffer` 底层是 `vector<char>`，通过 `readerIndex_` 和 `writerIndex_` 划分前置空间、可读区域和可写区域。业务读取时只移动 reader，下次空间不足时优先把未读数据搬到前面；仍然不够才扩容。这样可以减少频繁 erase 和重新分配。读完全部数据后，两个下标都复位到预留位置。

从 socket 读取时，应用事先不知道本次可读数据量。我的实现构造两个 `iovec`：第一块指向 Buffer 当前可写区，第二块指向栈上的 64 KB 临时数组，然后一次调用 `readv`。如果数据能放进现有空间，只推进 writer；如果超出，就把临时数组中的剩余部分 append 到 Buffer。它减少了“先扩容再读取”的次数，也只需要一次系统调用。需要强调的是，Buffer 只是字节流容器，不会自动解决 TCP 粘包；长度字段、分隔符或固定长度协议仍应由业务协议解析。

### 答题要点

- reader/writer 下标实现 O(1) 的消费和追加。
- 优先整理已有空间，不足时才扩容。
- `readv` 同时使用现有可写区和额外栈缓冲区。
- Buffer 保存字节流，消息边界必须由上层协议定义。

### 面试官追问

**追问 1：为什么 LT 模式下这里只调用一次 `readv` 也能工作？**  
**答：** LT 只要接收缓冲区仍有数据，fd 会继续保持可读，下一轮 epoll 还会通知，因此功能上不会丢数据；如果使用 ET，则通常要循环读取到 EAGAIN，否则可能不再收到边沿通知。

**追问 2：Buffer 会一直缩回初始大小吗？**  
**答：** 当前实现读完只复位下标，不主动缩容，所以经历过大报文的长连接可能长期保留较大容量。生产环境需要结合业务上限、收缩策略和内存监控处理。

## 8. `[S]` 非阻塞发送为什么需要输出缓冲区和 EPOLLOUT？

### 参考答案

非阻塞 socket 的一次 `write` 可能只写一部分，也可能因为内核发送缓冲区已满返回 EAGAIN。`TcpConnection::sendInLoop` 先判断当前是否已经关注写事件且输出缓冲区是否为空；如果都为空，就尝试直接写，减少一次内存拷贝。全部写完后可以异步触发发送完成回调。

如果还有剩余数据，就把它追加到 `outputBuffer_`，并给 Channel 注册 EPOLLOUT。内核发送缓冲区再次可写时，`handleWrite` 从输出缓冲区继续发送，移动 reader 下标；全部发送完后立刻取消 EPOLLOUT，否则“可写”通常长期成立，会造成事件循环忙转。如果连接处于 disconnecting，必须等待输出缓冲区清空后再 `shutdownWrite`，这相当于优雅关闭写端。项目还提供高水位回调，但它只是通知机制，不是完整的硬性背压。

### 答题要点

- 非阻塞写必须处理部分写和 EAGAIN。
- 空缓冲区时先直接写，剩余数据才进入用户态输出缓冲区。
- 只有存在待发送数据时才监听 EPOLLOUT，写完立即取消。
- 高水位回调用于告警或上层限流，本身不会自动阻止内存增长。

### 面试官追问

**追问 1：为什么不能从建立连接开始就永久监听 EPOLLOUT？**  
**答：** 大多数 socket 在大多数时间都是可写的，永久监听会让 epoll 持续返回写事件，即使应用没有数据要发，也会消耗 CPU 形成忙循环。

**追问 2：当前写路径还有什么重要边界没有处理好？**  
**答：** 当前源码使用 `write`，示例没有忽略 SIGPIPE，也没有使用 `MSG_NOSIGNAL`；对端关闭后写数据可能导致进程收到 SIGPIPE。错误路径和输出缓冲区上限也需要进一步完善。

## 9. `[S]` 项目中如何使用智能指针和 RAII 管理资源？有没有循环引用问题？

### 参考答案

资源所有权上，我尽量让“谁拥有资源、谁负责释放”保持清晰。`Socket` 是不可拷贝的 RAII 对象，析构时关闭 fd；`TcpConnection` 用 `unique_ptr` 独占 `Socket` 和 `Channel`；`EventLoop` 用 `unique_ptr` 管理 `Poller` 和 wakeup Channel；线程池也用 `unique_ptr` 管理每个 `EventLoopThread`。这样正常退出或异常展开时，不需要到处手写 delete 和 close。

连接需要被主循环、业务回调和异步任务共同临时持有，因此使用 `shared_ptr<TcpConnection>`，并让 `TcpConnection` 继承 `enable_shared_from_this`。Channel 不能反向长期持有连接的 shared_ptr，否则会和 TcpConnection 对 Channel 的所有权形成环，所以 `tie` 保存 weak_ptr，只在一次事件处理期间 lock 成局部 shared_ptr。回调使用 `std::function` 解耦组件，但绑定对象时仍必须关注捕获方式；当前部分路径绑定裸 `this`，说明“用了智能指针”并不等于生命周期自动绝对安全。

### 答题要点

- 独占资源使用 `unique_ptr`，共享连接生命周期使用 `shared_ptr`。
- Socket 析构关 fd，是最直接的 RAII 实践。
- `enable_shared_from_this` 让回调安全获得当前连接的共享所有权。
- Channel 用 weak_ptr 打破潜在所有权环，并在回调期临时保活。

### 面试官追问

**追问 1：为什么不能直接用 `shared_ptr<TcpConnection>(this)`？**  
**答：** 那会为同一个裸指针创建新的控制块，多个控制块都认为自己拥有对象，最终可能重复释放。`shared_from_this()` 返回的是原有控制块上的 shared_ptr，但前提是对象已经由 shared_ptr 管理。

**追问 2：RAII 能解决所有并发生命周期问题吗？**  
**答：** 不能。RAII 解决作用域和所有权释放，但跨线程任务仍要正确捕获对象与数据，并保证销毁顺序和线程归属。裸 `this`、悬空数据指针或数据竞争仍可能破坏安全性。

## 10. `[A]` 你是怎样测试 5000+ 并发连接的，约 12000 QPS 应该如何解释？

### 参考答案

我实际使用仓库中的 Python Echo 压测脚本做过测试。脚本为每个客户端建立 TCP 连接，循环发送固定消息并校验回显，同时统计成功请求和吞吐。这里有两个不能混在一起的观测：在较低并发的 Echo 测试中，我的重写版本大约达到 12000 QPS，参考源码的一次对照结果大约是 16000 QPS；把并发连接提高到 5000+ 后，连接仍能稳定建立并完成回显，但 QPS 会明显下降。因此 5000+ 是连接规模口径，12000 是另一组测试中的吞吐口径，不能说成“5000 并发下仍有 12000 QPS”。

我会严格限定这个数字的口径：它只对当时的测试环境、消息大小和脚本有效，不能直接外推到生产场景。压测客户端采用“一连接一 Python 线程”，线程调度、GIL、客户端和服务端是否争用同机资源，都可能先成为瓶颈；而当前服务端热路径还有大量同步 INFO 日志。更重要的是，当时没有保留 P95、P99 等延迟数据，所以我只能陈述并发连接数和约 12000 QPS，不能补造延迟、CPU或内存指标。

### 答题要点

- 已实测：5000+ 连接可工作但 QPS 会下降；较低并发下重写版本约 12000 QPS，参考源码约 16000 QPS。
- 明确结果是特定环境和脚本下的观测值，不包装成通用性能结论。
- Python 一连接一线程及同步日志都可能成为瓶颈。
- 没有延迟数据，就明确说没有，不虚构 P95/P99、CPU 或内存结果。

### 面试官追问

**追问 1：5000 个并发连接和 12000 QPS 是同一个概念吗？**  
**答：** 不是。并发连接数表示同时保持的 TCP 连接规模，QPS 表示单位时间完成的请求数；大量空闲长连接可能 QPS 很低，少量高频连接也可能有较高 QPS，二者必须分别描述。

**追问 2：如果重新做一次可信的压测，你会补充什么？**  
**答：** 我会固定硬件、系统参数、线程数、消息大小和持续时间，记录成功率、QPS、P50/P95/P99、CPU、内存和网络带宽；提高 `ulimit -n`，关闭热路径同步日志，并用多进程或专业压测工具把客户端与服务端分机部署。

## 11. `[A]` 你审查当前源码后发现了哪些缺陷？你会怎样修正？

### 参考答案

我不会把当前仓库描述成没有问题。最严重的一处是跨线程 `send`：代码把 `buf.c_str()` 和裸 `this` 绑定进延迟执行的回调，原字符串离开作用域后可能形成悬空指针。正确方向是按值捕获字符串，并用 `shared_from_this()` 保活连接。第二，`sendFile` 对未发送完的数据不断 `queueInLoop` 重试，没有把文件发送状态和 EPOLLOUT 正确整合，可能忙轮询，还没有管理文件 fd 的生命周期。

另外，`Acceptor` 忽略传入的 `reuseport` 参数而始终开启；epoll 创建调用把 `EPOLL_CLOEXEC` 传给了 `epoll_create`，应改成 `epoll_create1`；日志单例共享可变 `logLevel_`，时间格式化又使用 `localtime`，并发下不安全；热路径 INFO 日志还会显著影响性能。以上是我审查后识别出的当前缺陷和修正方案，不应说成已经全部修复并验证。

### 答题要点

- 跨线程 `send` 的字符串指针和裸 `this` 存在生命周期风险。
- `sendFile` 没有基于 EPOLLOUT 保存发送状态，可能自旋重试。
- `reuseport` 参数、`epoll_create1`、日志线程安全存在明确问题。
- 区分“已发现并能提出方案”和“已经修改、测试通过”，不虚构修复结果。

### 面试官追问

**追问 1：跨线程 `send` 应该怎样改才安全？**  
**答：** 投递任务时捕获 `TcpConnectionPtr self = shared_from_this()` 和一份字符串值，例如让 lambda 在 ioLoop 中调用 `self->sendInLoop(message.data(), message.size())`。这样对象和数据都会存活到回调执行结束。

**追问 2：非阻塞 `sendfile` 应怎样与 EventLoop 集成？**  
**答：** 需要把文件 fd、当前 offset 和剩余字节封装成连接的待发送状态；遇到部分发送或 EAGAIN 时注册 EPOLLOUT，写事件到来后继续，而不是立即反复投递。同时要定义文件 fd 的所有权和关闭时机，并与普通输出缓冲区保持顺序。

## 13. `[S]` 请介绍一下这个在线 OJ 项目，并说明一次代码提交的完整处理链路。

### 参考答案

我把系统拆成控制节点和编译服务两类进程。控制节点使用 cpp-httplib 接收请求，通过 MySQL 读取题目、预设代码、测试代码以及资源限制，再由 ctemplate 渲染题目列表和详情页。用户提交代码后，`/judge` 会拼接样例测试 `tail`，`/runtest` 会拼接正式判题代码 `test`；控制节点选择当前在途请求数最少的编译服务，通过 HTTP 调用它的 `/compile_and_run` 接口。编译服务先生成临时源文件，fork 子进程并 exec `g++` 完成编译；编译成功后再次 fork，在运行子进程中重定向标准输入、输出和错误，设置资源限制并 exec 用户程序。父进程通过 waitpid 回收子进程、解析退出状态，最后把状态、原因和输出封装为 JSON，沿原链路返回给页面。当前配置是同一台机器上的多个编译服务进程，主要验证服务拆分和进程级故障转移。

简历中的 C++11 指的是项目的主要语言特性和用户代码编译标准；当前仓库的服务端构建实际指定 C++17，因为代码中使用了 generic lambda。面试时我会把这两个口径分开说明，不会把当前构建参数说成 C++11。

### 答题要点

- 控制节点负责 HTTP 接入、题目查询、页面渲染、调度和结果汇总。
- 编译服务负责源码落盘、编译、受限运行和结果采集。
- 完整链路是“浏览器 → 控制节点 → 编译服务 → 子进程 → JSON 返回”。
- 当前是同机多进程实验架构，不应表述为跨机器分布式集群。

### 面试官追问

**追问 1：为什么要把控制节点和编译服务拆开？**

**答：** 编译和运行用户代码属于耗时且容易失败的工作，拆开后可以让控制节点专注于接入和调度，并让某个编译进程崩溃时不直接带走控制节点；同时编译服务可以按需增加实例。不过当前数据库和控制节点仍是单点，而且后端都在同一台机器上，所以可用性提升是有限的。

**追问 2：为什么简历写 C++11，而当前服务端按 C++17 构建？**

**答：** 项目的核心架构和大部分实现使用的是 C++11 能力，用户提交代码也通过 `g++ -std=c++11` 编译；但当前服务端排序代码使用了 generic lambda，CMake 和 makefile 因此指定 C++17。严格说当前仓库的服务端构建标准是 C++17，这一点需要按代码如实解释。

## 14. `[S]` 你的负载均衡是如何实现的？简历里写的“轮询”准确吗？

### 参考答案

严格按当前源码来说，简历中的“轮询”不准确，实际实现的是基于在途请求数的最小负载选择。控制节点启动时从配置文件读取多个编译服务地址，为每个节点维护一个 `load` 计数以及 online、offline 两个节点集合。每次判题时，我遍历在线节点，选择 `load` 最小的服务；发送请求前增加计数，请求结束后减少计数。

这样比单纯轮询多考虑了任务是否仍在执行，但它只反映请求数量，不能反映不同代码的真实编译成本。同负载时当前代码总是偏向配置靠前的节点，而且“选择节点”和“增加计数”不是一个原子步骤，并发下可能有多个请求同时选中同一节点。因此更准确的项目表述是“基于最少在途请求数的简单调度”，生产版本还需要原子预占和更公平的同负载选择。

### 答题要点

- 实际算法是 least-inflight，而不是轮询或随机。
- `load` 表示正在处理的请求数，不等同于 CPU、内存或队列长度。
- online/offline 列表和负载计数由互斥锁保护。
- 当前存在同负载偏置以及“选择后再加负载”的并发窗口。

### 面试官追问

**追问 1：怎样消除选择节点与增加负载之间的竞态？**

**答：** 我会把“扫描最小值、确定节点、给该节点加一”放在同一个临界区内，让选择动作同时完成负载预占；也可以把单机负载改为原子变量，但 online/offline 集合和选择过程仍需统一同步。请求结束时再用作用域守卫保证一定减回计数。

**追问 2：为什么最少请求数不一定代表真实负载最低？**

**答：** 不同提交的编译时间、运行时间和内存消耗差异很大，一个模板展开很重的编译任务可能比多个简单任务更贵。更完善的调度可以结合后端队列长度、CPU 利用率、历史耗时、节点权重和最大并发数，并设置背压，避免只看一个计数。

## 15. `[S]` cpp-httplib 如何处理并发请求？项目中的互斥锁保护了什么？

### 参考答案

我没有自行实现 HTTP 线程池，而是使用 cpp-httplib 自带的线程池模型。项目所带版本默认创建 `max(8, hardware_concurrency - 1)` 个工作线程，监听线程接收连接后把任务放入队列，由工作线程执行路由回调。因此多个请求会并发访问同一个 Control 和负载均衡器。我使用全局互斥锁保护 online、offline 节点集合，并为每台 Machine 的负载计数设置互斥锁，避免单次读写产生数据竞争。

不过当前 HTTP 调用、数据库查询、编译和 waitpid 都是阻塞式操作，一个判题请求会长期占用工作线程；默认任务队列也没有主动背压。我的准确表述应当是“基于 cpp-httplib 默认线程池处理并发，并对共享调度状态做基础同步”，不能说成自己实现了线程池，也不能把现有同步描述成完全无竞态。

### 答题要点

- 多线程能力来自 cpp-httplib 内置线程池，而非项目自研线程池。
- 路由回调并发执行，共享的节点集合和负载状态需要同步。
- 当前锁保护单次状态访问，但调度复合操作还不具备完整原子性。
- 判题链路是阻塞式的，线程数和后端处理能力共同限制吞吐。

### 面试官追问

**追问 1：为什么不直接把 `load` 全部改成 `std::atomic`？**

**答：** 原子变量只能保证单个计数操作原子，无法单独保证“遍历在线列表、比较多个节点、选择一个节点、完成预占”这一组操作的一致性。online/offline 容器的修改也仍需加锁，所以需要先定义清晰的锁粒度和复合操作边界，而不是简单把所有字段换成 atomic。

**追问 2：阻塞式线程池在这个项目中有什么风险？**

**答：** 一次提交会同步等待数据库、后端 HTTP、编译和用户程序退出，慢任务会一直占据工作线程。当工作线程全部被占用时，新连接只能排队，队列没有上限还可能放大内存压力。改进方向包括限制排队长度、设置连接和墙钟超时、为每个编译节点设置并发上限，并让超载请求快速失败。

## 16. `[S]` 为什么使用 `fork + exec + waitpid` 完成编译和运行？具体流程是什么？

### 参考答案

编译阶段，我先 fork 一个子进程，在子进程中把标准错误重定向到编译错误文件，然后通过 `execlp` 用 `g++ -std=c++11 -D COMPILER_ONLINE` 替换当前进程；父进程调用 waitpid 等待编译结束，并检查是否生成可执行文件。运行阶段再次 fork，子进程先完成标准流重定向和 setrlimit，再用 `execl` 加载刚生成的程序；父进程只负责等待和解析状态。

选择进程而不是在线程里直接执行用户代码，是因为 exec 会替换整个进程映像，而独立子进程还能让普通崩溃不直接破坏编译服务自身。waitpid 既能回收子进程，避免僵尸进程，也能拿到退出或信号终止信息。不过这种方式只提供基础进程隔离，不等于安全沙箱，而且当前从多线程 HTTP 服务中 fork，exec 前应尽量只调用异步信号安全函数。

### 答题要点

- 编译子进程 exec `g++`，运行子进程 exec 用户可执行文件。
- exec 替换子进程映像，不会替换父服务进程。
- waitpid 用于同步等待、回收子进程并取得终止状态。
- 子进程降低普通崩溃影响，但不能替代完整安全隔离。

### 面试官追问

**追问 1：fork 之后父子进程的内存和文件描述符是什么关系？**

**答：** 地址空间逻辑上相互独立，通常通过写时复制实现；父子进程各自有文件描述符表，但对应描述符会引用同一个内核打开文件对象，所以共享文件偏移和状态。项目在子进程中用 dup2 替换 0、1、2 后，应关闭不再需要的原始描述符，避免泄漏。

**追问 2：如果不调用 waitpid 会发生什么？**

**答：** 子进程退出后，内核仍需保留 PID 和退出状态供父进程读取，它会成为僵尸进程。大量僵尸会占用进程表项。waitpid 既完成资源回收，又让父进程获得退出码或终止信号，是判题状态生成的基础。

## 17. `[S]` 项目如何重定向并收集标准输入、标准输出和标准错误？

### 参考答案

我为每次任务生成对应的 stdin、stdout、stderr 临时文件。运行前先用 `open` 获得三个文件描述符，fork 后在子进程中通过 `dup2` 把它们分别复制到 0、1、2，再关闭原描述符，随后 exec 用户程序。这样程序仍然按普通方式读写标准流，但数据实际进入指定文件。编译阶段也使用同样思路，把 g++ 的标准错误单独重定向到 `compiler_error` 文件，因此编译失败时可以把诊断信息返回。父进程 waitpid 结束后读取 stdout 和 stderr，成功结果中各最多回传 64 KB；运行文件本身还设置了 4 MB 的文件大小限制。

需要明确的是，当前版本虽然建立了 stdin 重定向链路，但把请求中 `input` 写入 stdin 文件的代码被注释了，所以实际输入文件为空，不能声称已经完整支持自定义输入。

### 答题要点

- `dup2` 将临时文件替换为子进程的 0、1、2 号描述符。
- 编译错误和运行时 stderr 使用不同文件收集。
- 父进程等待结束后再读取输出，避免与子进程并发解析。
- 当前用户输入尚未真正写入 stdin，回答时必须说明边界。

### 面试官追问

**追问 1：为什么 `dup2` 后还要关闭原始文件描述符？**

**答：** dup2 成功后，新旧描述符都引用同一个打开文件对象，原描述符已经没有用途。如果不关闭，会造成描述符泄漏，并可能让依赖“所有写端关闭才读到 EOF”的逻辑迟迟不能结束。关闭原描述符不会影响已经复制到 0、1、2 的描述符。

**追问 2：为什么使用文件而不是管道？**

**答：** 文件实现简单，父进程可以等用户程序结束后一次性读取，也方便保留编译诊断；代价是有磁盘 I/O、临时文件清理和容量控制问题。管道更适合流式读取，但父进程必须并发消费 stdout 和 stderr，否则输出填满管道缓冲区后可能造成子进程阻塞。

## 18. `[S]` 你如何使用 `setrlimit` 限制用户程序？目前验证过哪些情况？

### 参考答案

运行子进程在 exec 前调用 setrlimit：`RLIMIT_CPU` 控制 CPU 时间，`RLIMIT_AS` 控制进程虚拟地址空间，`RLIMIT_FSIZE` 限制单个输出文件大小，避免无限输出写满磁盘。当前我实际验证过正确程序、死循环触发超时以及高内存程序触发内存超限这三类路径，没有做系统化压力测试，也没有吞吐或 P99 数据。

现有实现还有必须诚实说明的缺陷：代码只把 soft limit 设置为题目值，hard limit 设成无限，并且没有检查 setrlimit 返回值；数据库和页面按 KB 表示内存，而编译服务按 MB 换算，存在单位不一致。因此它证明了资源限制机制的基本流程，但不能宣称已经达到生产级可靠性。更严谨的实现应统一单位、检查每次调用，并把 hard limit 一并收紧，再由父进程增加墙钟定时器。

### 答题要点

- `RLIMIT_CPU`、`RLIMIT_AS`、`RLIMIT_FSIZE` 分别限制 CPU、地址空间和文件大小。
- 资源限制必须在运行子进程 exec 前设置。
- 实际只验证了正确、超时、内存超限三种情况，没有性能指标。
- 当前 hard limit、返回值检查和内存单位仍需改进。

### 面试官追问

**追问 1：CPU 时间限制为什么不能替代墙钟超时？**

**答：** `RLIMIT_CPU` 只累计进程真正占用 CPU 的时间，程序如果长期 sleep、阻塞 I/O 或等待锁，墙钟时间可能已经很长但 CPU 时间很少，父进程仍会卡在 waitpid。生产实现需要父进程维护截止时间，超时后杀死整个进程组并回收所有后代。

**追问 2：soft limit 和 hard limit 有什么区别？**

**答：** soft limit 是内核当前执行的限制，进程可以在不超过 hard limit 的范围内自行调整；hard limit 是上限，普通进程不能随意提高。当前把 hard limit 留为无限会让用户程序有机会重新提高 soft limit，因此更合理的是把 hard limit 也设置为受控值，并检查设置是否成功。

## 19. `[S]` 当前项目怎样判定编译错误、答案错误、超时和运行错误？

### 参考答案

当前编译阶段通过“是否形成可执行文件”判断是否成功；没有生成文件时读取 g++ 的错误输出，返回编译错误。运行阶段用 waitpid 得到原始状态：测试代码在答案不正确时调用 `exit(-5)`，当前实现通过原始状态值 `64256` 把它识别为答案错误；收到 `SIGXCPU` 映射为超时，`SIGABRT` 映射为内存超限，`SIGFPE` 映射为浮点错误，其余信号返回未知运行错误。

这个流程能支撑我验证过的正确、超时和内存超限场景，但状态解码方式不够规范。普通非零退出可能因为只取低 7 位而被误判成功，`SIGABRT` 也不一定由内存不足导致。正确做法是先用 `WIFEXITED`、`WEXITSTATUS`、`WIFSIGNALED` 和 `WTERMSIG` 分类，再结合父进程掌握的超时、内存和输出信息生成结果。

### 答题要点

- 编译错误来自 g++ 诊断，答案错误由测试代码的特殊退出码表示。
- 信号终止和正常退出必须分开解析。
- 当前魔数和位运算实现能跑通部分场景，但不够健壮。
- `SIGABRT` 不能被无条件等同于内存超限。

### 面试官追问

**追问 1：`WIFEXITED` 和 `WIFSIGNALED` 分别说明什么？**

**答：** `WIFEXITED(status)` 表示子进程通过 return、exit 或 `_exit` 正常结束，此时用 `WEXITSTATUS` 读取退出码；`WIFSIGNALED(status)` 表示进程被未处理信号终止，此时用 `WTERMSIG` 获取信号编号。只有先分类，退出码和信号才不会混淆。

**追问 2：为什么 `SIGABRT` 不一定表示内存超限？**

**答：** 用户主动调用 abort、断言失败、`std::terminate` 或未捕获异常都可能触发 SIGABRT。内存限制还可能表现为 `new` 抛出 `bad_alloc`、mmap 失败或其他信号，所以仅凭一个信号无法可靠判断 MLE；生产系统通常结合 cgroup 统计、内核事件和父进程监控判断。

## 20. `[S]` MySQL 在项目中保存什么？一次题目查询是怎样完成的？

### 参考答案

题库表保存题号、标题、难度、题目描述、预设代码、样例测试、正式判题代码，以及 CPU 和内存限制。控制节点的 Model 层对外提供查询全部题目和按题号查询单题两个主要接口。当前实现每次查询都会调用 `mysql_init` 和 `mysql_real_connect` 建立独立连接，设置 UTF-8 字符集，执行 SELECT，再通过 `mysql_store_result` 把各列映射到 Question，最后关闭连接。

这种写法简单，而且每个并发请求使用独立 MYSQL 句柄，不会共享一个连接，但连接创建成本较高。现有代码还使用硬编码账号、`select *` 和字符串拼接，查询不到题目时对空结果处理也不完善。后续应使用配置或环境变量、连接池、明确列名、预处理语句，并在访问结果第一行前检查行数。

### 答题要点

- 题库同时保存页面数据、测试代码和资源限制。
- Model 层提供题目列表查询和单题查询。
- 当前每次查询新建并关闭 MySQL 连接，没有连接池。
- 硬编码凭据、`select *` 和空结果处理是明确改进点。

### 面试官追问

**追问 1：为什么不能在多个线程之间直接共用同一个 MYSQL 连接？**

**答：** 同一连接上并发发送语句和读取结果容易让协议状态、结果集和错误信息相互干扰，除非在连接外再做严格串行化。服务端通常让一次请求独占一个连接，并由线程安全的连接池负责复用，这样既避免频繁握手，又保持请求之间的状态隔离。

**追问 2：按主键查询题号还需要额外建立索引吗？**

**答：** `number` 本身是主键，InnoDB 会建立聚簇索引，按题号等值查询已经可以利用主键索引，不需要再建一个重复索引。如果后续经常按难度、标题或提交时间筛选，再根据真实查询模式设计普通或联合索引。

## 21. `[S]` 提交记录是怎样实现的？为什么当前没有用户表？

### 参考答案

我实现的是最简单的无用户提交记录：每次正式提交完成后，把题号、提交代码、判题状态、原因、标准输出、标准错误和提交时间写入 `submissions` 表，并提供全量查询能力，用于查看系统收到过的所有提交。这个版本的目标是先打通“提交—判题—持久化—查询”链路，因此没有登录、用户 ID、权限和个人历史；所有记录都属于系统级公共记录。写入应发生在拿到判题结果之后，即使编译错误或答案错误也要保存，不能只记录通过的代码。

当前全量查询适合数据量很小的演示环境，但数据增长后会带来响应体、数据库扫描和代码隐私问题。下一步应增加用户体系、分页与条件过滤，并考虑代码字段的访问权限和保留策略。

### 答题要点

- `submissions` 记录题号、源码、状态、结果信息和提交时间。
- 正确、编译失败、运行失败等提交都应被记录。
- 当前没有用户维度，只提供系统全部提交的查询。
- 全量查询只适合小规模演示，后续必须增加分页、权限和过滤。

### 面试官追问

**追问 1：为什么提交记录要在判题结束后写入？**

**答：** 判题结束后才能同时保存最终状态、错误原因和输出，记录会更完整。若还要防止服务中途崩溃丢失提交，可以先插入一条 `PENDING` 记录取得 submission id，判题完成后再 UPDATE；当前简单版本采用完成后一次写入，链路更容易实现。

**追问 2：全量查询接口有什么问题？**

**答：** 数据量增加后会产生全表扫描、巨大响应和长时间占用连接，还会把所有用户代码直接暴露出去。改进时应按主键或提交时间倒序分页，只返回列表需要的摘要字段，查看源码需要单独接口和权限校验，并为常用过滤条件建立索引。

## 22. `[A]` 编译节点如何下线和恢复？当前可用性机制有哪些边界？

### 参考答案

控制节点维护 online 和 offline 两个节点集合。向编译节点发起 HTTP 请求时，如果连接失败，我先减少该节点的在途计数，再把它从 online 移到 offline，然后继续从剩余在线节点中选择服务，因此单个编译进程退出时，请求有机会转移到同机的其他进程。恢复采用人工触发：OJ 进程捕获 SIGQUIT，Linux 终端中按 `Ctrl+\` 会发送该信号，处理函数把 offline 中的节点全部重新移回 online。

这个设计用于演示节点摘除和恢复流程，不是完善的健康检查。它不会验证节点是否真的恢复，三个后端又都在同一台机器上；控制节点、MySQL 或整机故障仍会让系统不可用。信号处理函数当前还直接加锁，严格来说不符合异步信号安全要求，生产实现应使用 signalfd、自管道或原子标志把恢复工作交给正常线程。

### 答题要点

- 连接失败后节点从 online 移入 offline，并尝试其他在线节点。
- `Ctrl+\` 发送 SIGQUIT，当前实现一次性恢复全部离线节点。
- 恢复动作不做健康验证，属于人工重置而非自动探活。
- 同机多进程只能处理进程故障，无法处理主机和控制节点故障。

### 面试官追问

**追问 1：为什么不能在普通信号处理函数里直接加 mutex？**

**答：** 信号可能在持有同一把锁的线程上异步到达，处理函数再次加锁会永久死锁；mutex、iostream 和大部分库函数也不属于异步信号安全函数。更安全的方式是处理函数只写 eventfd、自管道或设置原子标志，再由事件循环或管理线程执行真正的恢复逻辑。

**追问 2：怎样实现自动恢复节点？**

**答：** 可以为离线节点记录失败次数和下一次探测时间，由后台线程按指数退避发送健康检查；连续成功达到阈值后再放回 online，避免节点在好坏状态间反复抖动。同时设置请求超时、重试上限和熔断窗口，全部节点不可用时明确返回 HTTP 503。

## 23. `[A]` 使用子进程运行用户代码是否已经实现了安全沙箱？

### 参考答案

没有。当前 fork 出独立进程可以隔离地址空间，让段错误等普通崩溃不直接破坏编译服务，并能在子进程上设置 rlimit，但用户程序仍与服务使用相同 UID，能访问该账号有权限读取的文件、网络和其他进程。项目没有 namespace、seccomp、cgroup、chroot、容器、进程数限制或独立低权限账号，用户代码还可以 fork 后台进程；编译服务监听 `0.0.0.0` 且没有鉴权，也不适合暴露到不可信网络。

另外，当前把测试代码直接拼接到用户代码中并依靠特殊退出码判断答案，用户代码如果提前 `exit(0)` 就可能绕过测试。因此我会把当前实现准确描述为“子进程级故障隔离和基础资源限制”，不会称为安全沙箱。生产化应把编译和运行都放进受控容器或 namespace/cgroup/seccomp 环境，并由可信父进程在外部比较输出。

### 答题要点

- fork 提供地址空间和普通崩溃隔离，不提供完整安全边界。
- 当前同 UID、可访问文件和网络，也没有限制派生进程。
- 测试代码与用户代码处于同一信任域，存在提前退出绕过问题。
- 生产环境需要降权、namespace、seccomp、cgroup 和外部判题。

### 面试官追问

**追问 1：用户程序 fork 子进程后自己退出会怎样？**

**答：** 当前父服务只 waitpid 直接子进程，后台后代可能继续运行，判题请求却已经返回并清理文件。改进时应为一次任务创建独立进程组或 PID namespace，超时和结束后杀死整个任务树，并通过 cgroup 对进程数、CPU 和内存做整体限制。

**追问 2：为什么编译阶段也要放进隔离环境？**

**答：** 恶意或极端 C++ 源码可以让 g++ 长时间占用 CPU、内存和磁盘，当前 rlimit 只设置在运行用户程序之前，保护不到编译器。编译阶段也需要请求大小限制、墙钟超时、CPU/内存/文件配额和低权限文件系统，必要时使用独立编译容器。

## 24. `[A]` 临时文件如何保证唯一？如果继续生产化，你会优先改什么？

### 参考答案

当前临时名由毫秒时间戳和一个静态 `atomic_uint` 组合，设计意图是避免同一编译服务内的并发冲突。但源码先读取 atomic，再单独执行 `id++`，这是两个独立原子操作，不是一次原子取号，两个线程仍可能拿到同一个值；同机多个编译进程的计数器也彼此独立，如果共享 `./temp`，还会发生跨进程冲突，错误清理甚至可能删除另一个任务的文件。

更可靠的做法是使用 `fetch_add` 修正线程内取号，并用 `mkstemp`/`O_EXCL`、PID 加随机数或每任务独立目录保证跨进程唯一，同时通过 RAII 清理。生产化时我会先修复判题正确性和安全边界：规范 waitpid 状态解析、把测试输出比较移到可信父进程、统一资源单位并增加 hard limit 和墙钟超时；之后再做容器化隔离、健康检查和背压，最后优化 MySQL 连接池、提交分页、监控和压力测试。

### 答题要点

- 当前“atomic 读取 + 自增”不是原子复合取号，仍有线程冲突。
- 同机多进程共享临时目录时，进程内计数器无法保证全局唯一。
- `mkstemp/O_EXCL`、独立任务目录和 RAII 能提升唯一性与清理可靠性。
- 生产化优先级应是正确性与安全，其次可用性、存储和性能。

### 面试官追问

**追问 1：为什么只把 `id++` 换成原子变量还不够？**

**答：** 当前 id 已经是原子变量，问题是“先 load、后 increment”分成了两步；需要用 `fetch_add(1)` 一次取得互不重复的旧值。即使线程内修好，不同进程仍有各自的原子变量，所以还要加入进程标识或直接使用内核提供的排他创建机制。

**追问 2：如果只能先做三项改造，你会选什么？**

**答：** 第一，使用标准 waitpid 宏并把测试结果比较放在可信父进程，先保证判题不被普通退出绕过；第二，为编译和运行增加墙钟超时、正确 hard limit、进程组回收和隔离环境；第三，修复负载预占与节点健康检查，在过载或全部离线时快速返回明确错误。监控和压测应随这三项一起补上，用数据验证效果。
