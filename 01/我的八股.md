# 一、C++ 语言、对象模型与 STL（1-18）

## 1. `[S]` 指针和引用有什么区别？函数参数应该如何选择？

### 参考答案

指针本质上是一个保存地址的对象，它可以为空、可以重新指向其他对象，也可以参与指针运算；引用是已有对象的别名，声明时通常必须绑定到一个有效对象，绑定后不能再改为引用另一个对象。对引用取地址得到的是被引用对象的地址，语义上更强调“这个对象一定存在”。

传参时，如果参数允许为空，或者函数需要修改指针本身的指向，使用指针；如果对象必须存在且需要修改对象，使用 `T&`；只读且对象较大时使用 `const T&`，避免拷贝；小型、拷贝成本低的标量类型通常直接值传递。现代 C++ 中还会用 `T&&` 表示移动语义或转发引用，但其语义不能简单等同于普通指针或左值引用。

### 答题要点

- 空值语义：指针可以是 `nullptr`，引用通常表达非空。
- 可重新绑定：指针可以，引用不可以。
- 使用场景：可选对象用指针，必选对象用引用，所有权用智能指针表达。
- 不要只回答“引用底层就是指针”；C++ 标准规定的是语义，不强制具体实现。

### 面试官追问

**追问 1：`sizeof(引用)` 得到什么？**  
**答：** 对表达式使用 `sizeof` 时，引用会表现为被引用对象，因此结果是被引用类型的大小。例如 `int& r = x; sizeof(r)` 通常等于 `sizeof(int)`。至于编译器是否为引用额外保存一个地址，以及对象布局中引用成员占多少空间，属于实现细节。

**追问 2：返回局部变量的引用有什么问题？**  
**答：** 普通局部变量在函数返回后生命周期结束，返回其引用或指针会形成悬空引用或悬空指针，后续访问是未定义行为。静态局部变量、全局对象，或生命周期由调用者保证的对象可以返回引用，但接口必须把生命周期约束表达清楚。

## 2. `[S]` `const`、`constexpr` 和 `mutable` 分别解决什么问题？

### 参考答案

`const` 表达运行期接口中的“不允许通过当前访问路径修改”。对指针来说要区分顶层 `const` 和底层 `const`：`int* const p` 表示指针本身不能改指向；`const int* p` 表示不能通过 `p` 修改目标对象。成员函数后的 `const` 表示该函数不能修改普通非静态数据成员，也不能调用非 `const` 成员函数。

`constexpr` 表示对象或函数具备在常量表达式中求值的能力。`constexpr` 对象必须在编译期初始化并且本身是常量；`constexpr` 函数在实参满足条件时可在编译期求值，否则也可以在运行期执行。`mutable` 允许某个数据成员在 `const` 成员函数中被修改，典型用途是缓存、统计信息或互斥锁，这些变化不改变对象对外可观察的逻辑状态。

### 答题要点

- `const` 重点是接口约束和 const-correctness，不等于对象永远不会变化。
- `constexpr` 重点是常量表达式和编译期计算能力。
- `mutable` 用于不影响逻辑状态的内部字段，不应滥用来绕过设计。

### 面试官追问

**追问 1：用 `const_cast` 修改一个 `const` 对象是否合法？**  
**答：** 如果原对象本来不是 `const`，只是通过 `const` 引用或指针访问，去掉限定后修改可以合法；如果原对象确实定义为 `const`，强行修改属于未定义行为，即使某次运行看起来成功也不能依赖。

**追问 2：`constexpr` 函数一定在编译期执行吗？**  
**答：** 不一定。只有在需要常量表达式并且实参与函数体都满足常量求值条件时才必须在编译期求值；在普通运行期上下文中，它可以像普通函数一样执行。

## 3. `[A]` `static` 在不同上下文中分别有什么含义？

### 参考答案

函数内的 `static` 局部变量具有静态存储期，只初始化一次，生命周期持续到程序结束，但作用域仍限制在函数内。C++11 起，函数内静态变量的初始化是线程安全的：多个线程首次同时进入时，只会有一个线程完成初始化，其他线程等待；但初始化完成后的对象访问是否线程安全仍由程序负责。

类中的静态数据成员属于类本身，而不是某个对象，所有实例共享；静态成员函数没有 `this` 指针，只能直接访问静态成员。命名空间或文件作用域下的 `static` 函数和变量具有内部链接，只在当前翻译单元可见。C++17 的 `inline static` 数据成员可以直接在类定义中完成定义，减少单独定义的需要。

### 答题要点

- 局部 `static`：静态生命周期、局部作用域、首次使用时初始化。
- 类 `static`：属于类，无 `this`。
- 文件作用域 `static`：内部链接，限制符号可见性。

### 面试官追问

**追问 1：局部静态变量的初始化线程安全，是否意味着使用也线程安全？**  
**答：** 不意味着。标准只保证初始化过程只发生一次；如果后续多个线程同时读写该对象，仍然需要互斥、原子变量或其他同步机制，否则可能发生数据竞争。

**追问 2：全局静态对象有什么常见风险？**  
**答：** 不同翻译单元之间的初始化和销毁顺序难以依赖，容易出现“静态初始化顺序问题”。常见规避方法是使用函数内静态对象，即 construct-on-first-use，或者减少跨翻译单元全局状态。

## 4. `[S]` C++ 的运行时多态是如何实现的？虚函数表里通常有什么？

### 参考答案

运行时多态依赖“通过基类指针或引用调用虚函数”。主流编译器通常在含虚函数的对象中放置一个隐藏的虚表指针 `vptr`，它指向该动态类型对应的虚函数表 `vtable`。虚表通常保存虚函数入口以及 RTTI 等相关信息。调用虚函数时，程序通过对象的 `vptr` 找到相应槽位，再间接调用实际覆盖函数。

`vptr/vtable` 是常见 ABI 实现方式，不是 C++ 标准强制规定的具体布局。虚调用通常比直接调用多一次间接寻址，还可能影响内联和分支预测，但在大多数业务代码中不应脱离性能数据过早优化。构造和析构期间，对象只被当作当前正在构造或析构的层次，虚调用不会分派到尚未构造或已经析构的派生部分。

### 答题要点

- 触发条件：虚函数 + 基类指针/引用 + 派生对象。
- 常见实现：对象有 `vptr`，类对应 `vtable`，调用时动态查表。
- 必须说明虚表是常见实现而非标准硬性规定。
- 构造、析构期间的虚调用不会正常下派到更派生类。

### 面试官追问

**追问 1：虚函数可以是静态成员函数吗？**  
**答：** 不可以。虚调用需要根据具体对象的动态类型分派，而静态成员函数没有 `this` 指针，不属于某个对象，因而不能是虚函数。

**追问 2：纯虚函数是否可以有定义？**  
**答：** 可以。`= 0` 使类成为抽象类并要求派生类覆盖，但纯虚函数仍可在类外提供定义，派生类也可以显式调用它。纯虚析构函数尤其必须提供定义，因为析构链最终仍会执行到基类析构部分。

## 5. `[S]` 为什么基类析构函数经常要声明为虚函数？

### 参考答案

如果一个派生对象通过基类指针被 `delete`，基类析构函数必须是虚函数，这样删除表达式才能先调用派生类析构，再调用基类析构，完整释放派生类资源。如果基类析构非虚，通过基类指针删除派生对象属于未定义行为，不只是“可能内存泄漏”这么简单。

并非所有基类都必须有虚析构。如果类型根本不准备被多态删除，可以把析构函数设为非虚并限制访问，例如设为 `protected`，防止外部通过基类指针删除。设计多态接口时通常遵循：析构函数要么 `public virtual`，要么 `protected non-virtual`。

### 答题要点

- 核心场景：通过基类指针删除派生对象。
- 非虚析构导致未定义行为。
- 虚析构会带来多态相关的对象空间和间接调用成本，但正确性优先。

### 面试官追问

**追问 1：构造函数为什么不能是虚函数？**  
**答：** 虚分派需要先存在一个具有确定动态类型的对象，而构造函数的任务正是建立对象及其动态类型；对象尚未构造完成时无法通过虚机制选择构造函数。若需要“虚构造”，通常使用工厂函数或虚拟 `clone()` 接口。

**追问 2：析构函数中调用虚函数会发生什么？**  
**答：** 在基类析构阶段，派生部分已经被销毁，对象被视为当前基类类型，因此调用的是当前层次的版本，不会分派到派生类。依赖析构期间的虚调用实现多态通常是危险设计。

## 6. `[S]` 函数重载、重写和隐藏有什么区别？

### 参考答案

重载发生在同一作用域，函数名相同但参数列表不同，编译器在编译期根据实参选择最合适版本；仅返回值不同不能构成重载。重写是派生类对基类虚函数提供相同签名的实现，运行时可通过虚分派调用派生版本，建议始终加 `override` 让编译器检查。

隐藏是名字查找规则造成的：派生类只要声明了与基类同名的函数，就可能把基类中该名字的所有重载隐藏，即使参数不同。可在派生类中写 `using Base::func;` 把基类重载引入当前作用域。`final` 可以阻止虚函数继续被重写，或阻止类继续被继承。

### 答题要点

- 重载：同一作用域，编译期，多参数列表。
- 重写：基类虚函数，派生类相同签名，运行期。
- 隐藏：名字查找行为，不要求参数相同。
- 工程实践：使用 `override` 和必要的 `using Base::func`。

### 面试官追问

**追问 1：派生类函数少写了一个 `const`，还能重写基类虚函数吗？**  
**答：** 不能。成员函数尾部的 `const` 是函数签名的一部分，会变成另一个函数并可能隐藏基类版本。使用 `override` 会让编译器直接报错，因此非常重要。

**追问 2：返回值不同为什么不能重载？**  
**答：** 调用点可能忽略返回值，编译器无法仅根据返回类型决定调用哪个函数。虚函数重写存在有限的协变返回类型例外，即返回派生类指针或引用可以覆盖返回基类指针或引用的函数。

## 7. `[S]` 什么是浅拷贝、深拷贝？Rule of Three、Five、Zero 分别是什么？

### 参考答案

浅拷贝按成员值复制。如果类拥有一个裸指针，浅拷贝只复制地址，两个对象会指向同一资源，可能导致重复释放、悬空访问或意外共享。深拷贝会为新对象分配独立资源并复制内容，使两个对象拥有彼此独立的生命周期。

如果类需要自定义析构函数、拷贝构造函数或拷贝赋值运算符中的任意一个，通常意味着它直接管理资源，三个往往都需要，这叫 Rule of Three。C++11 加入移动操作后扩展为 Rule of Five：再考虑移动构造和移动赋值。更推荐 Rule of Zero：把资源交给 `std::vector`、`std::string`、智能指针等 RAII 类型管理，让编译器生成正确的特殊成员函数。

拷贝赋值还需要处理自赋值和异常安全。copy-and-swap 先构造副本，再交换内部状态，可以自然处理自赋值并提供强异常保证，但可能有额外开销。

### 答题要点

- 先从“资源所有权”解释，不要只背五个函数名称。
- 深拷贝解决独立所有权；共享所有权应显式使用 `shared_ptr` 等表达。
- 优先 Rule of Zero，减少手写资源管理。

### 面试官追问

**追问 1：拷贝构造函数为什么通常接收 `const T&`？**  
**答：** 如果按值接收参数，为构造参数本身又需要调用拷贝构造，会形成无限递归；使用引用避免额外拷贝，使用 `const` 允许从常量对象和临时对象拷贝。

**追问 2：自赋值判断 `if (this == &rhs)` 是否总是必要？**  
**答：** 不是总要显式写。若实现先释放自身资源再读取右值，自赋值会出错，需要判断；copy-and-swap 等天然安全的实现可以不专门判断。关键是赋值操作在自赋值时仍保持正确。

## 8. `[S]` 什么是移动语义、右值引用和完美转发？

### 参考答案

移动语义的目标是把即将销毁对象所拥有的资源转移给新对象，避免昂贵的深拷贝。右值引用写作 `T&&`，能够绑定到右值。`std::move` 本身不移动任何东西，它只是把表达式转换为可被移动操作接收的右值类别；真正的资源转移发生在移动构造或移动赋值中。

移动后的对象必须保持“有效但状态未指定”，可以安全析构和重新赋值，但一般不能假设它为空。移动操作通常应标记 `noexcept`，因为 `std::vector` 扩容时为了维持强异常保证，往往只在移动构造不抛异常时优先移动，否则可能退回拷贝。

模板中的 `T&&` 在 `T` 由参数推导时是转发引用。结合引用折叠规则，`std::forward<T>(arg)` 可以保持调用者原始的左值/右值属性，这就是完美转发。普通的已命名右值引用变量本身是左值，继续转发时仍需 `std::move` 或 `std::forward`。

### 答题要点

- `std::move` 是类型转换，不等于实际搬运。
- 移动对象仍必须可析构、可赋值。
- `noexcept` 会影响容器是否敢于移动。
- 完美转发 = 转发引用 + 引用折叠 + `std::forward`。

### 面试官追问

**追问 1：返回局部对象时应不应该写 `return std::move(obj);`？**  
**答：** 通常不应该。编译器可进行 NRVO，把局部对象直接构造到返回位置；显式 `std::move` 可能阻止 NRVO。直接 `return obj;`，即使没有发生消除，语言规则也通常允许移动。

**追问 2：为什么一个类型定义了析构函数后，移动构造可能不再自动生成？**  
**答：** 用户声明某些特殊成员函数会抑制其他特殊成员函数的隐式生成，这是 Rule of Five 需要整体考虑的原因。工程上可显式写 `= default`，或采用 Rule of Zero 让成员类型负责资源管理。

## 9. `[S]` 什么是 RAII？它如何保证异常安全？

### 参考答案

RAII，即资源获取即初始化，把资源生命周期绑定到对象生命周期：构造成功后对象持有资源，析构时确定释放。栈对象在正常离开作用域和异常栈展开时都会析构，因此文件、锁、内存、socket 等资源可以自动释放，避免手写多条清理路径。`std::unique_ptr`、`std::lock_guard`、文件封装类都是典型 RAII。

异常安全通常分三级：基本保证是失败后对象仍有效、无资源泄漏，但状态可能变化；强保证是操作失败后状态与调用前相同，常通过“先在临时对象完成，再提交或交换”实现；不抛异常保证是操作承诺不抛，析构函数、移动操作和交换通常应尽量满足。RAII 是实现这些保证的基础，但并不会自动让所有业务状态具备强保证。

### 答题要点

- 资源不仅是内存，还包括锁、文件描述符、线程、事务等。
- 核心价值是把释放动作放入析构，覆盖正常和异常路径。
- 能说清基本保证、强保证、不抛保证。

### 面试官追问

**追问 1：析构函数可以抛异常吗？**  
**答：** 应避免。若栈展开过程中已经存在一个异常，析构函数再次抛出异常会触发 `std::terminate`。析构函数默认通常是 `noexcept`，内部清理失败应记录、吞掉可处理错误，或通过显式的 `close/commit` 接口提前报告。

**追问 2：`lock_guard` 为什么比手写 `lock()`/`unlock()` 好？**  
**答：** 手写方式遇到早返回或异常容易遗漏 `unlock()`；`lock_guard` 构造时加锁、析构时解锁，作用域结束必定释放，代码路径更容易证明正确。

## 10. `[S]` `unique_ptr`、`shared_ptr` 和 `weak_ptr` 应该如何选择？

### 参考答案

`unique_ptr` 表达独占所有权，不能拷贝、可以移动，空间和性能开销通常接近裸指针，应作为动态资源所有权的默认选择。`shared_ptr` 表达共享所有权，多个实例通过控制块维护强引用计数，最后一个强引用销毁时释放对象。它有原子计数、控制块和间接访问成本，不应因为“省事”而默认使用。

`weak_ptr` 是对 `shared_ptr` 管理对象的非拥有观察，不增加强引用计数。调用 `lock()` 可以在对象仍存活时取得一个 `shared_ptr`，否则得到空指针。它主要用于打破循环引用、缓存和观察者关系。裸指针或引用仍可用于“不拥有且调用期间确定有效”的访问，但接口需要明确生命周期。

### 答题要点

- 默认独占：`unique_ptr`。
- 确实存在共同生命周期才用 `shared_ptr`。
- `weak_ptr` 不延长对象生命，用来观察和打破环。
- 智能指针表达所有权，不是“所有指针全部替换为 shared_ptr”。

### 面试官追问

**追问 1：`make_shared` 相比 `shared_ptr<T>(new T)` 有什么优点？**  
**答：** 通常把对象和控制块放在一次分配中，分配次数少、局部性好，同时避免复杂表达式中的资源泄漏风险。代价是只要仍有 `weak_ptr`，合并分配的整块内存可能不能释放，即使对象已经析构；另外自定义内存布局时不一定适合。

**追问 2：可以用两个独立的 `shared_ptr` 接管同一个裸指针吗？**  
**答：** 不可以。它们会创建两个控制块，最终对同一对象删除两次，产生未定义行为。需要共享时应复制已有 `shared_ptr`；类内部要安全获得自己的 `shared_ptr`，可使用 `enable_shared_from_this`。

## 11. `[S]` `shared_ptr` 的引用计数是怎么工作的？为什么会循环引用？

### 参考答案

`shared_ptr` 通常包含对象指针和控制块指针。控制块保存强引用计数、弱引用计数、删除器、分配器等信息。强引用计数降到零时对象被销毁；弱引用计数也归零后控制块才被释放。复制和销毁不同 `shared_ptr` 实例时，对引用计数的修改需要线程安全。

引用计数不能处理拥有关系形成的环。例如 A 和 B 分别以 `shared_ptr` 持有对方，即使外部引用都释放，A、B 的强计数仍不为零，导致对象无法析构。应根据所有权语义把环中的至少一条边改为 `weak_ptr`，而不是在析构时手工“打环”。

引用计数线程安全不代表对象线程安全：多个线程操作彼此独立、但共享同一控制块的 `shared_ptr` 实例通常可以安全增减计数；若多个线程同时读写同一个 `shared_ptr` 变量，或并发访问其指向对象，仍需要相应同步。

### 答题要点

- 对象和控制块有不同释放时点。
- 循环引用的根因是强所有权形成环。
- 引用计数安全与被管理对象安全是两回事。

### 面试官追问

**追问 1：`weak_ptr::lock()` 为什么比先 `expired()` 再使用更好？**  
**答：** `expired()` 检查和后续获取之间存在竞态，对象可能刚好被其他线程销毁。`lock()` 原子地尝试把仍存活的对象提升为强引用，成功后所得 `shared_ptr` 在使用期间保证对象存活。

**追问 2：`enable_shared_from_this` 解决什么问题？**  
**答：** 它允许已经由 `shared_ptr` 管理的对象从成员函数中取得共享同一控制块的 `shared_ptr`，避免直接写 `shared_ptr<T>(this)` 创建第二个控制块。对象必须已经被某个 `shared_ptr` 接管，否则 `shared_from_this()` 会失败。

## 12. `[S]` `new/delete` 与 `malloc/free` 有什么区别？

### 参考答案

`malloc` 按字节分配原始内存，返回 `void*`，不调用构造函数；`free` 只归还内存，不调用析构函数。`new` 表达式先调用分配函数取得内存，再在其中构造对象；`delete` 先调用析构函数，再释放内存。普通 `new` 失败默认抛出 `std::bad_alloc`，`malloc` 失败返回空指针；`new (std::nothrow)` 则可返回空指针。

两组接口必须配对，不能 `malloc` 后 `delete`，也不能 `new` 后 `free`。数组还要匹配 `new[]/delete[]`，否则行为未定义。工程代码优先使用容器和智能指针，尽量不直接管理裸动态内存。

### 答题要点

- 最大区别不是语法，而是对象构造/析构语义。
- 分配失败行为不同。
- 必须成对使用；数组形式也要匹配。
- 现代 C++ 优先 RAII 容器和智能指针。

### 面试官追问

**追问 1：placement new 是什么？**  
**答：** placement new 不负责分配内存，而是在调用者给定的地址上构造对象，例如 `new (buffer) T(args...)`。使用结束时需要显式调用析构函数，底层内存再由原分配方式释放。内存池和容器底层实现经常使用它。

**追问 2：`delete nullptr` 是否安全？**  
**答：** 安全，它什么也不做。因此清理代码通常不需要先判断空指针。但悬空的非空指针、重复 `delete` 仍是未定义行为。

## 13. `[A]` 什么是内存对齐和结构体填充？如何估算 `sizeof`？

### 参考答案

处理器通常对按自然边界对齐的数据访问更高效，有些架构甚至要求特定对齐。编译器会在结构体成员之间和末尾插入填充字节，使每个成员地址满足其对齐要求，并让结构体大小是其最大对齐要求的整数倍，以保证结构体数组中每个元素都正确对齐。

估算时，从偏移 0 开始，依次把每个成员放到满足自身对齐的位置，最后把总大小补齐到结构体整体对齐的整数倍。成员排序会影响填充量，把大对齐成员集中放在前面通常能减少空间浪费，但不能为了省几个字节破坏接口、序列化协议或 ABI。`#pragma pack` 可改变布局，但可能降低访问效率并带来跨平台问题。

### 答题要点

- 成员起始地址满足自身对齐。
- 结构体总大小满足最大成员对齐。
- 成员顺序可能改变大小。
- 多态对象通常还含实现相关的虚表指针。

### 面试官追问

**追问 1：为什么结构体末尾也可能有填充？**  
**答：** 为了让结构体数组中的下一个元素起始地址仍满足结构体的最大对齐要求。如果没有尾部填充，第二个元素中的高对齐成员可能落在错误边界上。

**追问 2：能否直接把结构体内存写入网络作为协议？**  
**答：** 通常不应该。结构体可能存在填充、字节序差异、类型宽度和 ABI 差异，也可能泄露未初始化填充字节。网络协议应显式定义字段宽度、顺序和字节序并序列化。

## 14. `[S]` `std::vector` 的底层原理是什么？扩容时发生什么？

### 参考答案

`vector` 使用一段连续内存保存元素，通常维护首地址、当前元素末尾和容量末尾，因此可 O(1) 随机访问，缓存局部性好。`size` 是已构造元素数量，`capacity` 是当前内存最多可容纳的元素数量。

当追加元素超过容量时，`vector` 会申请更大的连续内存，把旧元素移动或拷贝到新内存，销毁旧元素并释放旧内存。增长倍率由实现决定，不能回答成标准固定“两倍”。因为扩容不是每次都发生，尾部追加的均摊复杂度是 O(1)，单次扩容则是 O(n)。

扩容会使所有指向旧内存的指针、引用和迭代器失效。提前知道数量时可用 `reserve` 减少扩容；`resize` 会改变元素数量并构造或销毁元素，两者不能混淆。`shrink_to_fit` 只是非强制请求，不保证释放容量。

### 答题要点

- 连续存储、随机访问 O(1)、缓存友好。
- 扩容：重新分配 + 移动/拷贝 + 释放旧内存。
- 增长倍率实现相关，追加是均摊 O(1)。
- `reserve` 改容量，`resize` 改元素个数。

### 面试官追问

**追问 1：扩容时为什么有时拷贝而不是移动？**  
**答：** 为保持强异常保证，如果类型的移动构造可能抛异常而拷贝构造可用，标准库实现可能选择拷贝。把正确的移动构造标记为 `noexcept` 能让容器更放心地移动。

**追问 2：`emplace_back` 一定比 `push_back` 快吗？**  
**答：** 不一定。`emplace_back(args...)` 可直接在容器尾部构造元素，能避免某些临时对象；如果已经有一个 `T` 对象，`push_back(std::move(t))` 与之可能同样高效。还要警惕 `emplace` 的隐式构造使代码语义不清。

## 15. `[S]` `vector`、`deque`、`list` 应该怎样选择？

### 参考答案

默认优先 `vector`：连续内存带来较好的缓存局部性，随机访问 O(1)，尾部追加均摊 O(1)，真实性能常优于只看复杂度得到的结论。`deque` 通常由分段连续内存组成，支持两端 O(1) 插入删除和 O(1) 随机访问，但整体不连续，缓存和迭代器规则更复杂。

`list` 是双向链表，已知位置的插入删除是 O(1)，迭代器通常稳定，也适合 `splice`；但查找位置仍是 O(n)，每个节点有指针开销，分散分配造成缓存不友好。实际服务端代码中，除非确实需要稳定迭代器、频繁中间拼接或删除，不能仅凭“O(1) 插入”就选择 `list`。

### 答题要点

- 默认 `vector`，原因是连续性和局部性。
- `deque` 适合双端操作。
- `list` 的 O(1) 删除要求已经拿到迭代器，不包含查找成本。
- 选择容器要结合访问模式、内存和迭代器稳定性。

### 面试官追问

**追问 1：为什么 `list` 的插入 O(1) 仍可能比 `vector` 慢？**  
**答：** 若需要先遍历找位置，总成本是 O(n)；节点分配和指针跳转还会增加分配器开销和缓存未命中。`vector` 移动一段连续的简单对象可能非常快。

**追问 2：需要频繁从头部插入，应选什么？**  
**答：** 通常先考虑 `deque`，它支持两端高效插入删除。若还要求节点级稳定性或链表拼接，再考虑 `list`；应以真实访问模式和基准测试为准。

## 16. `[S]` `map` 和 `unordered_map` 有什么区别？

### 参考答案

`map` 通常由平衡搜索树实现，主流实现是红黑树。查找、插入、删除复杂度为 O(log n)，元素按键有序，范围查询方便，插入通常不会使其他元素的迭代器失效。`unordered_map` 是哈希表，平均查找、插入、删除为 O(1)，最坏可能退化到 O(n)，不维护顺序。

哈希表需要哈希函数和相等比较保持一致：如果两个键相等，它们的哈希值必须相同。负载因子过高时会 rehash，桶数量改变，迭代器失效，操作可能出现一次 O(n) 开销。面对不可信输入时，还要考虑恶意构造哈希碰撞造成的性能攻击。

选择时不能只看平均复杂度：需要有序遍历、范围查询、稳定时延时倾向 `map`；追求平均点查性能且有可靠哈希函数时倾向 `unordered_map`。

### 答题要点

- `map`：有序、O(log n)、树结构。
- `unordered_map`：无序、平均 O(1)、哈希碰撞和 rehash。
- 复杂度之外还要谈顺序、内存、缓存、最坏时延。

### 面试官追问

**追问 1：为什么哈希冲突不可避免？**  
**答：** 键空间通常远大于有限桶空间，根据抽屉原理，不同键可能映射到同一桶。实现会用链式结构或开放寻址等方法处理冲突，好的哈希函数只是让分布更均匀，不能消灭冲突。

**追问 2：`unordered_map::reserve` 有什么意义？**  
**答：** 根据预期元素数量提前准备足够桶，减少插入过程中的 rehash 次数。它可以改善性能并降低迭代器频繁失效的风险，但仍要结合最大负载因子。

## 17. `[S]` 常见 STL 容器的迭代器失效规则是什么？

### 参考答案

`vector` 扩容后所有迭代器、指针和引用失效；未扩容时，在插入点及其后的迭代器通常失效。删除时，删除点及其后的迭代器失效。`list` 插入通常不使现有迭代器失效，删除只使被删元素的迭代器失效。

`map/set` 插入通常不使现有迭代器失效，删除只影响被删元素。`unordered_map/set` 插入若触发 rehash，会使迭代器失效，但已有元素的引用和指针通常仍有效；删除使被删元素相关引用和迭代器失效。`deque` 的规则更复杂，中间插入删除通常会广泛失效，两端操作也要区分迭代器与引用，工程中应查具体标准接口保证。

循环删除时使用 `it = container.erase(it)` 接收下一个有效迭代器，不要在迭代器失效后再执行 `++it`。

### 答题要点

- `vector` 重点记扩容和删除。
- 链表、树容器通常只使被删节点失效。
- 哈希容器重点记 rehash。
- 能写出安全的遍历删除模式。

### 面试官追问

**追问 1：为什么 `vector` 扩容会使所有迭代器失效？**  
**答：** 元素被移动或拷贝到一块新的连续内存，旧地址整体不再保存那些对象，因此所有指向旧地址的迭代器、指针和引用都失效。

**追问 2：怎样在遍历 `vector` 时删除满足条件的所有元素？**  
**答：** 可使用 erase-remove idiom：先用 `std::remove_if` 把保留元素移动到前部，再调用 `erase` 删除尾部区间；C++20 可用 `std::erase_if`。如果必须逐个处理，则使用 `it = v.erase(it)`。

## 18. `[A]` Lambda、`std::function` 和 `std::bind` 的原理与使用区别是什么？

### 参考答案

Lambda 表达式会生成一个匿名闭包类型，捕获的数据成为闭包对象的成员，调用运算符保存函数体逻辑。值捕获保存声明时的副本，引用捕获保存引用语义，必须确保被捕获对象在回调执行时仍存活。默认情况下，值捕获 Lambda 的调用运算符是 `const`；加 `mutable` 后可修改闭包内部副本，但不会修改外部原对象。

`std::function<R(Args...)>` 是通用可调用对象包装器，通过类型擦除保存函数指针、Lambda、仿函数等。它方便统一回调接口，但可能存在间接调用、对象存储和动态分配开销。`std::bind` 可绑定部分参数并生成新的可调用对象，但占位符、值类别和重载处理容易降低可读性；现代 C++ 通常优先使用 Lambda。

### 答题要点

- Lambda 是具体匿名类型，不天然等于函数指针。
- 捕获方式决定状态和生命周期风险。
- `std::function` 提供类型擦除，便利但并非零开销。
- 新代码通常用 Lambda 替代复杂 `bind`。

### 面试官追问

**追问 1：捕获 `this` 有什么生命周期风险？**  
**答：** 捕获 `this` 本质上保存对象指针，并不会延长对象生命周期。若异步回调晚于对象析构执行，就会悬空。共享所有权场景可捕获 `shared_ptr`，非拥有观察可捕获 `weak_ptr` 并在执行时 `lock()`。

**追问 2：无捕获 Lambda 能转换为函数指针吗？**  
**答：** 满足签名条件的无捕获 Lambda 可以转换为普通函数指针；有捕获 Lambda 需要保存状态，不能直接转换为普通函数指针，通常通过模板参数或 `std::function` 传递。

# 二、C++ 多线程与并发（19-26）

## 19. `[S]` `mutex`、`recursive_mutex`、`shared_mutex` 有什么区别？RAII 锁如何选择？

### 参考答案

`std::mutex` 提供普通互斥，同一时刻只允许一个线程进入临界区；同一线程重复加锁会出问题。`recursive_mutex` 允许同一线程递归加锁并按次数解锁，但它经常掩盖职责不清或递归调用设计问题，应谨慎使用。`shared_mutex` 支持多个读者持有共享锁，或一个写者持有独占锁，适合读多写少且临界区有一定工作量的场景；若读写都很短，管理开销可能得不偿失。

锁应由 RAII 包装。`lock_guard` 简单、固定持锁整个作用域；`unique_lock` 可延迟加锁、提前解锁、转移所有权，也是条件变量所需的锁类型；C++17 的 `scoped_lock` 可同时锁多个互斥量，并使用避免死锁的算法。不要手写多个可能提前返回的 `lock()/unlock()` 路径。

### 答题要点

- 先说明互斥、递归互斥、读写锁的语义。
- RAII 保证异常和早返回路径正确解锁。
- 锁类型选择必须结合读写比例、竞争程度和临界区长度。

### 面试官追问

**追问 1：互斥锁保护的到底是什么？**  
**答：** 锁保护的不是某个变量在语言层面的“绑定关系”，而是一条访问共享状态的协议。所有访问同一不变量的线程都必须遵守同一把锁，否则即使写代码时“某变量旁边有锁”，仍然会发生数据竞争。

**追问 2：读多写少就一定适合 `shared_mutex` 吗？**  
**答：** 不一定。共享锁本身有更复杂的状态维护，可能出现写者饥饿，短临界区下开销也可能高于普通互斥锁。应通过压力测试判断；也可考虑复制后发布、分片或无锁读等其他方案。

## 20. `[S]` 原子变量和 CAS 是什么？它们能完全替代互斥锁吗？

### 参考答案

原子操作保证某次读、写或读改写在并发观察下不可被拆分，不会出现中间状态。CAS，即 compare-and-swap，在内存值等于期望值时把它更新为新值，否则返回当前值；C++ 中对应 `compare_exchange_weak/strong`。许多无锁结构通过“读取旧值 - 计算新值 - CAS 提交 - 失败重试”实现。

原子变量不能完全替代互斥锁。单个计数器、标志位适合原子；如果需要同时维护多个变量的不变量，或临界区包含复杂操作，单独把每个字段变成原子仍无法保证组合操作的一致性。并且 `std::atomic<T>` 不保证所有类型、所有平台都真正 lock-free，可用 `is_lock_free()` 查询。

`compare_exchange_weak` 允许即使值相等也偶发失败，适合放在循环中，某些架构上更高效；`strong` 不允许这种伪失败，适合不循环或失败代价较高的场景。

### 答题要点

- CAS 是带条件的原子读改写。
- 无锁不等于无竞争；高竞争时 CAS 自旋也可能很昂贵。
- 单变量状态适合原子，复合不变量通常更适合锁。

### 面试官追问

**追问 1：`volatile` 能实现线程同步吗？**  
**答：** 不能。C++ 的 `volatile` 主要阻止编译器省略对特殊内存的访问，常用于内存映射 I/O；它不提供原子性，也不建立线程间 happens-before 关系。线程同步应使用原子变量、互斥锁等。

**追问 2：无锁一定比有锁快吗？**  
**答：** 不一定。无锁算法避免线程因互斥锁阻塞，但可能产生大量 CAS 重试、缓存行争用和更复杂的内存回收成本。低竞争、复杂临界区或可维护性优先时，成熟的互斥锁可能更快、更可靠。

## 21. `[A]` 什么是 C++ 内存模型？`relaxed`、`acquire/release`、`seq_cst` 有何区别？

### 参考答案

C++ 内存模型规定多个线程对内存操作如何排序和可见。若两个线程无同步地并发访问同一内存位置，至少一个是写，并且不是合适的原子操作，就发生数据竞争；数据竞争在 C++ 中属于未定义行为。不能用“在我的 CPU 上测试没问题”证明正确。

`memory_order_relaxed` 只保证该原子操作本身不可分割，不提供与其他普通内存操作的跨线程排序，适合不依赖先后关系的计数。释放操作之前的写，在另一个线程以获取操作读到对应值后对它可见，这形成 release-acquire 同步，适合安全发布对象。`seq_cst` 在 acquire/release 基础上还为所有顺序一致原子操作建立单一全局顺序，最容易推理，也是默认内存序，但可能限制优化。

典型发布模式是：生产者先填充普通数据，再对原子标志做 release 存储；消费者以 acquire 读取到该标志后，就能看到此前数据写入。内存序是高级优化点，若没有严格证明，优先使用锁或默认顺序一致语义。

### 答题要点

- 数据竞争是未定义行为。
- `relaxed` 只保原子性；acquire/release 建立可见性；`seq_cst` 还给出统一总序。
- 必须结合 happens-before 解释，而不是只说“禁止重排”。

### 面试官追问

**追问 1：原子变量本身线程安全，为什么还会读到旧数据？**  
**答：** 原子性只保证该变量的操作不可撕裂。若使用 `relaxed`，它不会把其他普通数据的写入与这个原子标志建立同步；另一个线程即使看到标志变化，也不一定因此获得其他写入的可见性保证。

**追问 2：`acquire` 和 `release` 应分别用在哪一侧？**  
**答：** 发布数据的一侧通常对同步原子做 release 写；消费数据的一侧对同一同步关系做 acquire 读。只有 acquire 确实读到了 release 写入的值或其 release sequence，才建立同步关系。

## 22. `[S]` 条件变量为什么必须配合互斥锁和条件谓词使用？

### 参考答案

条件变量用于让线程在“某个共享状态满足条件前”高效睡眠。`wait(lock, pred)` 的核心动作是：检查谓词；若不满足，则原子地释放互斥锁并进入等待；被唤醒后重新获取锁，再次检查谓词。原子释放并等待避免了“检查完条件、尚未睡眠时通知已经发生”的丢失唤醒窗口。

条件变量允许虚假唤醒，而且通知只表示“状态可能变化”，不保证当前线程拿到锁时条件仍成立，所以必须在循环中检查谓词。推荐直接使用带谓词的重载。修改共享状态时要持有同一把锁，通知可在解锁前或解锁后进行；很多场景先修改、解锁、再通知可减少被唤醒线程立刻竞争锁，但正确性取决于共享状态和锁协议，而不是通知本身是否持锁。

### 答题要点

- 等待的是共享状态，不是等待一次通知。
- `wait` 原子地“解锁并休眠”，返回前重新加锁。
- 必须用谓词循环处理虚假唤醒和竞争。

### 面试官追问

**追问 1：先 `notify_one`，后 `wait` 会怎样？**  
**答：** 条件变量本身不保存通知。如果没有由共享状态和谓词记录事件，通知发生时没有等待者，该通知会丢失。正确设计应先改变受锁保护的状态，等待者即使稍后进入也能通过谓词发现条件已经满足。

**追问 2：什么时候使用 `notify_one`，什么时候使用 `notify_all`？**  
**答：** 一份资源只够一个等待者消费时通常用 `notify_one`，减少惊群；状态变化可能让多个等待者同时满足，或不同等待者谓词不同而无法确定唤醒谁时使用 `notify_all`。仍需基于性能测试和正确性选择。

## 23. `[S]` 死锁产生的必要条件是什么？工程中如何避免？

### 参考答案

经典死锁有四个必要条件：互斥使用资源、持有并等待、资源不可抢占、循环等待。四者同时成立时才可能死锁。最常见的代码原因是多个线程以不同顺序获取多把锁，例如线程 A 先锁 L1 再锁 L2，线程 B 先锁 L2 再锁 L1。

工程上最有效的方法是建立全局锁顺序，所有路径按同一顺序加锁；使用 `std::scoped_lock` 或 `std::lock` 一次协调多把锁；缩小临界区，不在持锁期间做阻塞 I/O、回调或调用未知代码；复杂系统中可采用超时、try-lock、锁层级检查和监控。调试时可采集所有线程栈，观察它们分别持有什么锁、等待什么锁，构造等待图。

### 答题要点

- 能完整说出四个必要条件。
- 重点措施：固定锁顺序、RAII、多锁原子协调、缩小临界区。
- 不要把“加超时”说成根治；它更多是故障恢复手段。

### 面试官追问

**追问 1：活锁和饥饿与死锁有什么区别？**  
**答：** 死锁中线程互相等待且都无法继续；活锁中线程仍不断执行和让步，但状态反复变化而没有有效进展；饥饿是某个线程长期得不到资源，而其他线程仍可推进。

**追问 2：只有一把互斥锁会死锁吗？**  
**答：** 也可能，例如普通 `mutex` 被同一线程重复加锁，或持锁调用回调后回调再次请求同一锁。递归锁能绕过某些自锁，但更应检查调用层级和职责设计。

## 24. `[S]` 如何设计一个基本线程池？有哪些容易忽略的问题？

### 参考答案

基本线程池包含固定或动态数量的工作线程、任务队列、互斥锁、条件变量和停止状态。提交任务时把可调用对象放入队列并通知工作线程；工作线程循环等待“队列非空或正在停止”，取出任务后应在锁外执行，避免长任务阻塞其他线程取任务。若需要返回值，可把任务包装为 `packaged_task` 并向调用者返回 `future`。

必须明确关闭语义：停止接收新任务后，是处理完队列再退出，还是立即取消；析构时要通知所有线程并 `join`，不能让线程访问已销毁的池对象。生产环境还要考虑有界队列和背压，否则请求增长快于处理能力时，队列会无限占用内存并放大延迟。任务异常要被捕获或通过 `future` 传递，不能让异常逃出线程入口导致 `std::terminate`。

### 答题要点

- 组件：工作线程、任务队列、锁、条件变量、停止标志。
- 锁内取任务，锁外执行任务。
- 关闭、异常、有界队列、背压是高频追问。
- 线程数不是越多越好，要区分 CPU 密集和 I/O 密集。

### 面试官追问

**追问 1：CPU 密集任务的线程数如何估计？**  
**答：** 起点通常接近可用 CPU 核数，避免过多上下文切换；若有超线程、NUMA 或其他进程竞争还需实测。I/O 密集任务因线程经常等待，可适当增加，但服务端更应考虑异步 I/O 和整体负载。

**追问 2：任务队列为什么最好有界？**  
**答：** 无界队列把过载隐藏成内存增长和排队延迟，最终可能使整个进程崩溃。有界队列迫使系统在过载时明确选择阻塞、拒绝、降级或让调用方重试，这就是背压。

## 25. `[A]` 如何实现线程安全的单例？双重检查锁为什么容易写错？

### 参考答案

C++11 后最简洁可靠的方式是函数内静态对象：

```cpp
class Singleton {
public:
    static Singleton& instance() {
        static Singleton obj;
        return obj;
    }
private:
    Singleton() = default;
};
```

语言保证该局部静态对象只初始化一次，即使多个线程首次并发调用也安全。也可以用 `std::call_once` 和 `std::once_flag` 完成一次初始化。

传统双重检查锁的问题是“分配内存、构造对象、发布指针”可能被编译器或处理器重排，另一个线程可能看到非空指针却读到未完全构造的对象。C++11 后可以用正确的原子 acquire/release 语义实现，但代码复杂、容易出错，通常没有必要。

### 答题要点

- 首选 C++11 函数内静态对象。
- 初始化线程安全不代表单例内部状态线程安全。
- 双重检查锁涉及发布顺序和内存模型，不建议手写。

### 面试官追问

**追问 1：单例对象的销毁顺序有风险吗？**  
**答：** 有。多个静态对象在程序退出时互相依赖可能出现销毁顺序问题。可通过减少全局依赖、显式管理生命周期，或在确有理由时设计进程结束不销毁的对象规避，但不能随意泄漏资源。

**追问 2：为什么单例常被认为不利于测试？**  
**答：** 它引入隐藏的全局状态和隐式依赖，测试之间容易相互污染，也难以替换实现。更可测试的方式是依赖注入，把所需服务显式传给使用者。

## 26. `[A]` 什么是假共享？CAS 中的 ABA 问题又是什么？

### 参考答案

假共享是指多个线程修改逻辑上互不相关的变量，但这些变量恰好位于同一缓存行。缓存一致性以缓存行为单位，一个核写入会使其他核中的同一行失效，导致缓存行在核之间反复转移，吞吐显著下降。可通过线程私有计数后汇总、数据分片、调整布局或用 `alignas` 把热点字段分离来缓解，但填充会增加内存占用，需要用性能工具验证。

ABA 是 CAS 的经典问题：线程读到值 A 后暂停，其他线程把它改为 B 又改回 A，原线程 CAS 只比较当前值，误以为状态从未变化。无锁栈中，这可能对应节点已被弹出、释放甚至地址被复用。常见方案是给指针附加版本号形成 tagged pointer，或使用 hazard pointer、epoch-based reclamation 等安全内存回收机制。

### 答题要点

- 假共享的竞争单位是缓存行，不是源代码变量。
- ABA 的关键是“值相同不代表期间没有变化”。
- 两者都是无锁/高并发代码中需要基准和严格证明的问题。

### 面试官追问

**追问 1：怎样确认是假共享而不是普通锁竞争？**  
**答：** 先用 `perf stat`、`perf c2c` 等工具观察缓存未命中和缓存行争用，再通过分离字段、线程本地化等实验对照吞吐。不能只看到多线程扩展差就直接下结论。

**追问 2：无锁结构为什么特别难做内存回收？**  
**答：** 一个线程从共享结构摘除节点后，其他线程可能仍持有该节点地址并准备访问。立即释放会造成 use-after-free，不释放又会泄漏；必须证明没有线程再访问，hazard pointer 和 epoch 机制就是为这种安全回收建立协议。

# 三、计算机网络与 Linux 网络编程（27-36）

## 27. `[S]` TCP 和 UDP 的核心区别是什么？如何选择？

### 参考答案

TCP 是面向连接的可靠字节流协议。建立连接后提供有序、无重复的字节传输，并通过序列号、确认、重传、流量控制和拥塞控制实现可靠性。它不保留应用层消息边界，应用必须自行设计协议分帧。

UDP 是无连接的数据报协议，每次发送对应一个数据报，保留消息边界，但不保证送达、顺序或不重复。它头部小、无需握手，应用可自行决定可靠机制和时延策略，适合 DNS、实时音视频、游戏以及基于 UDP 实现的 QUIC 等。不能笼统说 UDP 一定更快；最终性能取决于网络、协议机制和业务目标。

### 答题要点

- TCP：连接、可靠、有序、字节流、拥塞与流量控制。
- UDP：无连接、数据报、消息边界、可靠性由应用决定。
- 选择依据是可靠性、时延、消息语义和实现成本。

### 面试官追问

**追问 1：UDP 调用 `connect` 后还是 UDP 吗？**  
**答：** 还是 UDP。`connect` 可在内核中记录默认对端，使应用可直接 `send/recv`，并能接收某些异步错误、过滤其他来源的数据报，但不会产生 TCP 握手，也不会自动提供可靠传输。

**追问 2：UDP 数据报过大会怎样？**  
**答：** 超过路径 MTU 时可能发生 IP 分片，任一分片丢失都会导致整个数据报无法重组，可靠性和性能都变差；若启用禁止分片，发送可能失败。应用通常控制报文大小或实现分片与重组，并尽量避免依赖 IP 分片。

## 28. `[S]` TCP 为什么需要三次握手？两次为什么不够？

### 参考答案

三次握手过程是：客户端发送 `SYN` 和初始序列号 x；服务端回复 `SYN+ACK`，确认 x+1，同时给出自己的初始序列号 y；客户端再发送 `ACK` 确认 y+1。完成后双方都确认了自己的发送能力、接收能力以及对方的发送和接收能力，并同步了两个方向的初始序列号。

若只有两次，服务端发送 `SYN+ACK` 后无法确认客户端是否收到了自己的序列号和连接确认，也更难避免网络中延迟到达的旧 SYN 让服务端建立无效连接。第三次 ACK 让服务端确认客户端仍然有效且已收到服务端信息。三次握手还会协商 MSS、窗口扩大、SACK、时间戳等选项。

### 答题要点

- 双向同步初始序列号。
- 第三次让服务端确认客户端收到了服务端的 SYN。
- 能解释旧报文和半开连接，而不是只背状态名。

### 面试官追问

**追问 1：第三次握手可以携带应用数据吗？**  
**答：** 普通 TCP 中可以，客户端在连接状态允许后可让第三个 ACK 携带数据；服务端一般要等握手完成后再向应用交付。TCP Fast Open 还可在满足条件时让 SYN 阶段携带数据，但需要专门机制处理安全和重放。

**追问 2：SYN Flood 如何攻击服务端？**  
**答：** 攻击者发送大量 SYN 却不完成第三次握手，使服务端半连接队列和相关资源耗尽。缓解手段包括 SYN cookies、合理 backlog、限速、缩短重试以及网络层防护，但要结合正常流量特征。

## 29. `[S]` TCP 为什么通常四次挥手？什么是半关闭？

### 参考答案

TCP 是全双工连接，两个方向需要独立关闭。主动关闭方发送 FIN，表示自己不再发送数据；被动方先 ACK，但它可能还有数据未发送，因此不能总把自己的 FIN 与 ACK 合并。等被动方发送完毕后，再发送 FIN，主动方回复最后 ACK，所以通常是四个报文。

半关闭表示一个方向已经关闭，另一个方向仍可传输。例如调用 `shutdown(fd, SHUT_WR)` 后，本端不再发送并向对端发 FIN，但仍可以接收对端剩余数据。若被动方在收到 FIN 时也没有数据要发，ACK 和 FIN 可能合并，所以抓包不一定总看到严格四个独立报文。

### 答题要点

- TCP 双向独立关闭是四次的根本原因。
- FIN 表示“这个方向没有更多数据”，不是立即销毁整个连接。
- `shutdown` 能精确控制方向，`close` 释放本进程的文件描述符引用。

### 面试官追问

**追问 1：进程退出后 socket 会怎样？**  
**答：** 内核会关闭进程持有的文件描述符，TCP 按相应关闭语义处理。若还有其他通过 `dup` 或 `fork` 共享同一 open file description 的描述符引用，只有最后一个引用关闭时才真正触发完整关闭行为。

**追问 2：收到 FIN 后，`read` 一定立刻返回 0 吗？**  
**答：** 如果接收缓冲区还有未读数据，应先把数据读完；之后 `read` 才返回 0 表示有序 EOF。返回 0 与暂时没有数据的 `EAGAIN` 含义不同。

## 30. `[S]` `TIME_WAIT` 和 `CLOSE_WAIT` 分别为什么产生？过多说明什么？

### 参考答案

`TIME_WAIT` 通常出现在主动关闭方，它在发送最后 ACK 后等待 2MSL。作用一是如果最后 ACK 丢失，能接收对方重传的 FIN 并再次 ACK；作用二是让旧连接中延迟报文在网络中消失，避免污染相同四元组的新连接。它是 TCP 正确性机制，不应一看到就当成故障。

`CLOSE_WAIT` 出现在被动关闭方：内核已经收到对端 FIN 并向本地应用交付 EOF，但应用还没有关闭自己的 socket。少量短暂存在正常，持续大量通常说明程序没有在 EOF 或异常路径调用 `close`，或者某个业务逻辑长期阻塞。

服务端出现大量 `TIME_WAIT` 先看它是否承担主动关闭角色、短连接比例和连接复用策略；不能盲目修改内核参数。大量 `CLOSE_WAIT` 更应优先检查应用的文件描述符生命周期和线程栈。

### 答题要点

- `TIME_WAIT`：主动关闭方，2MSL，保证最后 ACK 和旧报文隔离。
- `CLOSE_WAIT`：被动方已收 FIN，但应用未关闭。
- 两者排查方向完全不同。

### 面试官追问

**追问 1：为什么是 2MSL？**  
**答：** MSL 是报文段在网络中的最大生存时间。等待两个方向各一个 MSL 的量级，可以覆盖最后 ACK 到达以及对端 FIN 重传返回的往返，并让旧报文基本退出网络。

**追问 2：`SO_REUSEADDR` 是否等于可以无条件复用任意连接？**  
**答：** 不是。它主要影响本地地址绑定规则，例如服务重启时更容易重新绑定处于某些状态的本地端口；不能破坏仍有效连接四元组的唯一性，也不是消除 `TIME_WAIT` 的万能开关。

## 31. `[S]` TCP 如何实现可靠传输？

### 参考答案

TCP 把字节编号，通过序列号标识报文段数据范围；接收方使用确认号表示下一个期望字节。校验和检测传输错误，滑动窗口允许多个报文在未确认时同时在途，提高带宽利用率。若超时未确认，发送方根据动态估算的 RTO 重传；收到多个重复 ACK 时可触发快速重传。接收方负责重排乱序数据并去除重复数据，应用最终看到有序字节流。

TCP 通常采用累积确认，即 ACK n 表示 n 之前的字节已经按序收到；SACK 选项能告诉发送方额外收到的非连续区间，使丢包时更精确重传。可靠不等于消息一定被对端业务处理：写成功通常只表示数据进入本机协议栈，业务级成功还需要应用层响应、幂等和超时机制。

### 答题要点

- 序列号、ACK、校验和、超时/快速重传、滑动窗口、乱序重排。
- RTO 根据 RTT 动态估算，不是固定值。
- 传输层可靠与业务处理成功要区分。

### 面试官追问

**追问 1：为什么不能把 RTO 简单设为固定很小的值？**  
**答：** 网络 RTT 会波动，固定过小会产生大量误重传并加剧拥塞，固定过大又会让真实丢包恢复太慢。TCP 根据采样 RTT 及其波动动态估计 RTO，并采用退避。

**追问 2：接收方发了 ACK，数据就一定已经被应用读取了吗？**  
**答：** 不一定。ACK 表示数据已被对端 TCP 协议栈接收，通常进入接收缓冲区，不代表对端进程已经读取、更不代表业务处理完成。

## 32. `[S]` TCP 流量控制和拥塞控制有什么区别？

### 参考答案

流量控制保护接收端，避免发送速度超过接收应用和接收缓冲区的处理能力。接收方在 ACK 中通告接收窗口 `rwnd`，发送方未确认的在途数据不能超过该窗口。若窗口变为零，发送方会使用持续计时器等机制探测窗口是否重新打开。

拥塞控制保护网络，避免过多数据注入链路造成路由器队列溢出和拥塞崩溃。发送方维护拥塞窗口 `cwnd`，依据丢包、RTT 或显式信号调整。经典思路包括慢启动、拥塞避免、快速重传和快速恢复；Linux 还可能使用 CUBIC、BBR 等具体算法。实际可发送窗口受 `min(rwnd, cwnd)` 限制。

### 答题要点

- 流量控制看接收方能力，对应 `rwnd`。
- 拥塞控制看网络承载能力，对应 `cwnd`。
- 实际发送量同时受两者约束。

### 面试官追问

**追问 1：慢启动为什么叫“慢”，窗口增长却很快？**  
**答：** 它相对“直接以很大速率发送”而言从较小窗口开始探测容量；在每个 RTT 内窗口大致指数增长，因此数值上并不慢。达到阈值或出现拥塞信号后转入更保守的拥塞避免。

**追问 2：接收窗口很大，吞吐就一定高吗？**  
**答：** 不一定。吞吐还受拥塞窗口、RTT、丢包率、应用读写速度、socket 缓冲区和路径带宽等限制。高带宽长时延网络还需足够窗口扩大能力才能填满带宽时延积。

## 33. `[S]` 什么是 TCP 粘包和拆包？如何正确解决？

### 参考答案

所谓“粘包/拆包”的根本原因是 TCP 提供连续字节流，不保留应用调用 `send` 的消息边界。一次 `send` 的内容可能被分成多次 `recv` 返回，多次 `send` 的内容也可能一次读到；此外 `send/recv` 本身都可能只处理部分字节。这不是 TCP 出错，而是应用层协议必须解决的分帧问题。

常见方案有固定长度、特殊分隔符、长度前缀，以及固定头部中携带正文长度。服务端应维护每连接输入缓冲区：循环读入数据，先判断是否足够解析头部，再校验长度上限，正文完整后取出一帧，剩余字节继续留在缓冲区。必须限制最大包长，防止恶意长度导致内存耗尽。

### 答题要点

- TCP 是字节流，没有消息边界。
- 不能假定一次 `send` 对应一次 `recv`。
- 长度字段协议最常用，需处理半包、多包和非法长度。
- 写侧同样要处理 partial write。

### 面试官追问

**追问 1：UDP 有粘包问题吗？**  
**答：** UDP 保留数据报边界，一次接收对应一个数据报，不会把两个数据报合成一个；但接收缓冲区太小时数据报可能被截断，数据报也可能丢失、乱序或重复。

**追问 2：使用分隔符协议有什么风险？**  
**答：** 正文中可能出现分隔符，需要转义或编码；还要限制在找不到分隔符时缓冲区的最大长度，否则攻击者可持续发送无分隔符数据耗尽内存。

## 34. `[S]` 阻塞/非阻塞与同步/异步有什么区别？

### 参考答案

阻塞与非阻塞描述一次调用在条件暂不满足时是否让调用线程等待。阻塞 socket 的 `read` 在无数据时可能睡眠；非阻塞 socket 会立即返回 `EAGAIN/EWOULDBLOCK`，调用者稍后重试。它们关注的是调用行为。

同步与异步描述 I/O 完成由谁推进以及如何通知。同步 I/O 中，即使先用 epoll 等待就绪，真正的 `read/write` 仍由应用线程调用并完成数据搬运；异步 I/O 是应用提交请求后，内核或运行时完成操作，再以完成事件通知应用。因此“非阻塞”不自动等于“异步”，epoll + non-blocking 通常仍归为同步非阻塞 I/O。

### 答题要点

- 阻塞维度：调用是否等待。
- 同步维度：应用等待就绪后自己执行，还是系统完成后通知结果。
- epoll 通常是就绪通知，不是完整异步完成通知。

### 面试官追问

**追问 1：非阻塞 `connect` 一般如何判断连接成功？**  
**答：** `connect` 可能返回 `EINPROGRESS`，随后关注可写事件；事件到达后用 `getsockopt(fd, SOL_SOCKET, SO_ERROR, ...)` 检查最终结果，不能仅凭“可写”认定成功。

**追问 2：非阻塞 `read` 返回 `EAGAIN` 表示什么？**  
**答：** 表示当前没有数据可立即读取，不是连接关闭，也不是永久错误。连接有序关闭时，在缓冲区读空后 `read` 返回 0。

## 35. `[S]` `select`、`poll` 和 `epoll` 有什么区别？

### 参考答案

`select` 每次调用都要传入并更新位图集合，通常受 `FD_SETSIZE` 限制，内核和用户态需复制集合，返回后应用还要线性扫描所有 fd。`poll` 使用 `pollfd` 数组，取消固定大小位图限制，但每次仍传递完整数组并线性扫描。

`epoll` 通过 `epoll_ctl` 把关注集合维护在内核中，`epoll_wait` 主要返回已就绪事件，应用不必每次传全部 fd 或扫描全部关注项，更适合大量连接、少量活跃的场景。其内部常见实现包含用于维护关注项的树结构和就绪链表，但面试时不要绝对化为“所有操作都是 O(1)”：增删关注项、事件触发、锁竞争和回调都存在成本。

连接数少或大多数连接始终活跃时，epoll 优势可能不明显；选择还要考虑平台、编程模型和实际负载。

### 答题要点

- `select`：位图、数量限制、每次复制和扫描。
- `poll`：数组、无固定 fd 位图上限，但仍扫描。
- `epoll`：内核维护关注集，返回就绪项，适合大量低活跃连接。
- 避免背诵“epoll 永远 O(1)、永远更快”。

### 面试官追问

**追问 1：epoll 为什么适合高并发连接？**  
**答：** 它把长期关注集合留在内核，每次等待主要向用户返回就绪事件，开销更接近活跃连接数量，而不是每轮扫描所有连接；因此在连接很多但同时活跃比例低时优势明显。

**追问 2：epoll 惊群是什么？**  
**答：** 多个线程或进程等待同一监听事件时，一个连接到来可能唤醒多个等待者，只有一个成功处理，其他产生无效竞争。可通过合理的 accept 分发模型、`EPOLLEXCLUSIVE` 等机制缓解，具体行为取决于内核和架构。

## 36. `[S]` epoll 的 LT、ET 有什么区别？Reactor 模型如何工作？

### 参考答案

LT（水平触发）中，只要 fd 仍处于可读或可写状态，`epoll_wait` 就会持续报告，编程相对稳健。ET（边缘触发）通常只在状态从未就绪变为就绪时通知，因此收到事件后必须使用非阻塞 fd，循环读或写直到返回 `EAGAIN`，否则剩余数据可能不会再次触发通知，连接就会“卡住”。

Reactor 是就绪事件驱动模型：事件循环等待一组 fd 就绪，将事件分派给对应处理器，处理器再执行 `accept/read/write` 等同步非阻塞操作。单 Reactor 可处理所有事件；主从 Reactor 中，主循环负责监听和接收连接，子循环负责已连接 socket 的 I/O。跨线程投递任务时，常用 `eventfd` 或 pipe 唤醒阻塞在 `epoll_wait` 的事件循环。

Proactor 则更强调提交异步操作，由系统完成 I/O 后通知完成结果。Linux 上典型 Reactor 更常见；`io_uring` 等提供了更接近异步完成的能力。

### 答题要点

- LT：条件仍满足就重复通知；ET：主要通知状态变化。
- ET 必须非阻塞并读写到 `EAGAIN`。
- Reactor = 等待就绪、分发事件、应用执行 I/O。
- 能解释主 Reactor、子 Reactor 和跨线程唤醒。

### 面试官追问

**追问 1：ET 模式下一次最多读固定 4 KB 可以吗？**  
**答：** 不可靠。若 socket 中还有数据但本次没有读到 `EAGAIN`，之后可能没有新的边缘事件，剩余数据长期得不到处理。应循环读取并把数据交给应用缓冲区，直到 `EAGAIN`、EOF 或真实错误。

**追问 2：为什么 `eventfd` 适合唤醒事件循环？**  
**答：** 它本身是可被 epoll 监控的文件描述符。其他线程写入计数值后，等待线程收到可读事件并取出任务，可把“用户态任务到达”统一纳入 fd 事件循环；相比普通 pipe，它接口更轻量、语义更贴合事件通知。

# 四、操作系统与 Linux 系统编程（37-46）

## 37. `[S]` 进程、线程和协程有什么区别？

### 参考答案

进程是资源隔离和保护的基本单位，拥有独立虚拟地址空间、页表和多种内核资源；线程是 CPU 调度的基本单位，同一进程内线程共享代码、堆、全局数据和文件描述符表等资源，但各自有寄存器、程序计数器、栈和线程局部存储。线程间通信方便，但一个线程的非法内存访问可能破坏整个进程。

协程通常是用户态调度的轻量执行单元。多个协程可运行在一个或多个线程上，通过显式或运行时控制的挂起与恢复切换，切换成本通常低于内核线程；但阻塞系统调用若未被异步化，可能阻塞承载它的整个线程。协程提升的是并发组织和等待效率，不会自动提供 CPU 并行。

### 答题要点

- 进程重隔离，线程重调度与共享，协程重用户态协作式切换。
- 线程有独立栈和寄存器，但共享进程地址空间。
- 并发不等于并行；单线程协程不能同时使用多个 CPU 核。

### 面试官追问

**追问 1：线程切换一定比进程切换快吗？**  
**答：** 通常更轻，因为同进程线程共享地址空间，往往不需切换页表；但仍要保存恢复寄存器、进入调度器，并可能破坏缓存局部性。具体成本取决于是否跨核、工作集和系统实现，不能绝对化。

**追问 2：一个进程崩溃会影响另一个进程吗？**  
**答：** 内存隔离通常能阻止直接破坏另一个进程，但共享资源、IPC、文件、服务依赖或整个机器资源耗尽仍可能产生间接影响。隔离是边界，不等于完全无关联。

## 38. `[S]` 什么是虚拟内存？它解决了哪些问题？

### 参考答案

每个进程看到的是自己的虚拟地址空间，CPU 通过页表把虚拟页映射到物理页或其他后备存储。虚拟内存带来三类核心能力：隔离与保护，不同进程默认不能直接访问彼此内存；地址抽象，程序不必关心物理内存连续位置；灵活映射与按需分配，同一物理页可以被共享，文件可被 `mmap` 到地址空间，尚未真正访问的页可以暂不分配物理内存。

典型进程地址空间包含代码段、只读数据、已初始化/未初始化全局数据、堆、内存映射区和栈，但具体布局受系统、架构和 ASLR 影响。虚拟地址不等于已经占用同等物理内存，实际常在首次访问发生缺页时建立映射。

### 答题要点

- 地址转换：虚拟页 - 页表 - 物理页。
- 三个价值：隔离、抽象、按需与共享映射。
- 虚拟空间大小、已提交内存和实际驻留物理内存不是一回事。

### 面试官追问

**追问 1：为什么 64 位进程看起来有很大地址空间，却不能真的分配那么多内存？**  
**答：** 虚拟地址空间只是可寻址范围，实际可用还受有效地址位数、物理内存、交换空间、内核提交策略、进程资源限制和映射数量影响。申请成功也不一定说明物理页已经全部分配。

**追问 2：多个进程能映射同一物理页吗？**  
**答：** 可以。共享库代码页、共享内存、文件映射都可能让多个虚拟地址映射到同一物理页，并通过页权限控制读写。这也是高效 IPC 和减少内存重复的重要基础。

## 39. `[S]` 什么是缺页异常和 TLB？一次内存访问大致经历什么？

### 参考答案

CPU 使用虚拟地址访问内存时，先从 TLB 查找最近的虚拟页到物理页映射。TLB 命中后可快速组合物理地址；未命中时需要进行页表遍历，找到有效页表项后填充 TLB。若页表项表明页面当前不在物理内存、尚未分配或访问权限不满足，则触发缺页异常进入内核处理。

匿名页首次访问、写时复制都可能产生不需要磁盘 I/O 的 minor page fault；若页面需要从文件或交换空间读入，属于 major page fault，成本高得多。非法地址或权限无法解决时，内核最终可能向进程发送 `SIGSEGV`。大页能降低页表层级和 TLB 压力，但会增加内部碎片并影响分配灵活性。

### 答题要点

- TLB 是页表映射缓存，不是普通数据缓存。
- TLB miss 不等于 page fault；前者可能只需页表遍历。
- 缺页也不一定访问磁盘，要区分 minor/major。

### 面试官追问

**追问 1：上下文切换会清空 TLB 吗？**  
**答：** 取决于架构和系统实现。切换地址空间时必须避免使用旧进程映射；现代 CPU 可通过 ASID/PCID 给 TLB 项打地址空间标签，减少完全刷新，但仍可能有相关成本。

**追问 2：什么是写时复制？**  
**答：** 多个地址空间先共享只读物理页；当某一方尝试写入时触发缺页，内核复制该页并给写入者建立私有可写映射。`fork` 常借此避免立即复制父进程全部内存。

## 40. `[S]` 用户态和内核态有什么区别？系统调用的过程是什么？

### 参考答案

用户态代码运行在较低特权级，不能直接执行特权指令或任意访问硬件和内核内存；内核态具有高权限，负责调度、内存管理、文件系统、网络和设备驱动。隔离的目的在于把应用错误限制在进程边界，并由内核统一检查资源访问。

系统调用是用户程序请求内核服务的受控入口。库函数封装参数后执行特定指令进入内核，CPU 切换特权级和栈，内核校验参数、执行服务，再返回用户态。它涉及模式切换和安全检查，但不必然发生线程调度意义上的上下文切换；调用可能立即返回，也可能阻塞并触发调度。

### 答题要点

- 特权和隔离是用户态/内核态的核心区别。
- 系统调用会发生态切换，但不一定发生进程/线程切换。
- 库函数不等于系统调用，例如部分内存分配可在用户态缓存中完成。

### 面试官追问

**追问 1：函数调用和系统调用有什么区别？**  
**答：** 普通函数调用通常只在同一特权级内改变控制流和栈帧；系统调用通过受控入口进入内核，涉及特权级、内核栈、参数验证和内核服务，成本通常更高。

**追问 2：为什么不能让应用直接操作网卡？**  
**答：** 直接操作会破坏隔离、安全和资源公平，多个进程也难协调。内核驱动统一管理设备并提供受检查的接口；某些高性能方案可受控地绕过部分内核路径，但仍需 IOMMU、权限和资源隔离。

## 41. `[S]` 什么是上下文切换？它的成本来自哪里？

### 参考答案

线程被调度切出时，系统要保存程序计数器、栈指针、通用寄存器和必要的处理器状态，选择另一个可运行线程，再恢复其状态。若切换到不同进程，还可能切换地址空间相关状态。上下文切换可以由时间片用完、阻塞 I/O、锁等待、中断或更高优先级任务触发。

成本不仅是保存和恢复寄存器。新任务的代码和数据可能不在 CPU 缓存中，分支预测状态和 TLB 局部性也会受影响；线程过多还增加调度器和运行队列压力。因此服务端不能用无限线程处理无限连接，要结合事件驱动、线程池和任务拆分控制切换。

### 答题要点

- 直接成本：保存/恢复执行状态和调度。
- 间接成本：缓存、TLB、分支预测和核间迁移。
- 阻塞、抢占、主动让出都可能触发切换。

### 面试官追问

**追问 1：如何查看进程的上下文切换情况？**  
**答：** 可用 `pidstat -w`、`vmstat`、`perf stat` 等观察自愿和非自愿上下文切换，再结合 CPU 利用率、运行队列和线程栈定位原因。

**追问 2：自愿与非自愿上下文切换有什么区别？**  
**答：** 自愿切换通常是线程因 I/O、锁、条件变量等主动进入不可运行状态；非自愿切换通常是时间片耗尽或被更高优先级任务抢占。两者比例能帮助判断是等待过多还是调度竞争严重。

## 42. `[S]` Linux 常见进程间通信方式有哪些？如何选择？

### 参考答案

常见 IPC 包括匿名管道、命名管道、消息队列、共享内存、信号量、信号、Unix domain socket 和网络 socket。匿名管道适合有亲缘关系进程的单向字节流；命名管道可由无亲缘进程通过路径访问。消息队列提供消息边界和一定内核管理。

共享内存让多个进程直接映射同一物理页，数据传输开销低，但必须另配互斥量、信号量或原子协议解决同步和一致性。Unix domain socket 支持本机双向通信、消息或字节流语义，还可传递文件描述符，接口和网络 socket 类似。信号适合异步通知，不适合承载大量数据。

选择时考虑数据量、消息边界、是否跨机器、同步复杂度、可靠性和可维护性。吞吐最高不等于总体方案最好。

### 答题要点

- 能列出至少管道、共享内存、消息队列、socket、信号。
- 共享内存快在少拷贝，但同步最复杂。
- 跨机器只能选择网络通信类方案。

### 面试官追问

**追问 1：共享内存为什么还需要同步？**  
**答：** 多进程可同时访问同一数据，若没有互斥或原子协议，就可能读到中间状态、覆盖写入或发生内存序问题。共享只解决“看见同一块内存”，不自动解决并发正确性。

**追问 2：匿名管道为什么通常说是半双工？**  
**答：** 一个管道有读端和写端，数据沿一个方向流动。若父子进程需要双向独立通信，通常创建两条管道，或直接使用全双工 Unix domain socket。

## 43. `[S]` Linux 文件描述符的本质是什么？`dup` 和 `fork` 后有什么变化？

### 参考答案

文件描述符是进程文件描述符表中的一个小整数索引。表项指向内核的 open file description，后者通常保存当前文件偏移和状态标志，再关联到具体 inode、socket 或 pipe 等内核对象。因此 socket 也可通过文件描述符使用统一的 `read/write/close` 接口。

`dup` 产生一个新的 fd，但新旧 fd 指向同一个 open file description，因此共享文件偏移和文件状态标志；每个 fd 自己的 close-on-exec 标志可以不同。`fork` 后父子进程的 fd 表被复制，但对应表项仍引用相同的 open file descriptions，所以它们也可能共享文件偏移。只有相关引用计数归零时，内核对象才真正关闭。

### 答题要点

- fd 不是文件本身，是当前进程表中的索引。
- fd 表项、open file description、底层对象是不同层次。
- `dup/fork` 后可能共享偏移和状态。
- `0/1/2` 通常对应标准输入、输出、错误。

### 面试官追问

**追问 1：为什么关闭一个重复 fd 后另一个仍能使用？**  
**答：** `close` 只移除当前 fd 表项并减少引用计数；另一个 fd 仍指向同一 open file description，只要引用还在，底层对象不会被最终关闭。

**追问 2：`FD_CLOEXEC` 有什么作用？**  
**答：** 设置后，执行 `exec` 成功时内核自动关闭该 fd，防止不应继承的文件或 socket 泄漏到新程序。多线程环境通常优先在创建 fd 时原子设置 `O_CLOEXEC` 等标志，避免创建与设置之间的竞态。

## 44. `[S]` 什么是零拷贝？`sendfile` 和 `mmap` 各减少了什么？

### 参考答案

传统“读文件再发 socket”通常经历：磁盘经 DMA 到内核页缓存；`read` 把数据复制到用户缓冲区；`write` 再复制到 socket 内核缓冲区；网卡经 DMA 发送，同时还伴随多次用户态/内核态切换。所谓零拷贝是相对减少 CPU 参与的数据复制和切换，并不表示系统中绝对没有任何数据移动。

`sendfile` 让内核直接把文件页缓存中的数据交给 socket 发送路径，避免数据往返用户态；支持 scatter-gather 等机制时还可进一步减少内核内复制。`mmap` 把文件页映射到进程地址空间，应用可直接访问页缓存，省去 `read` 到用户缓冲区的一次复制，但访问会产生缺页，并且发送时仍可能需要其他处理。Linux 还有 `splice` 等在内核对象间移动数据的接口。

### 答题要点

- 先描述传统路径，再说明减少了哪次复制/切换。
- “零拷贝”是相对术语，不是数据完全不移动。
- `sendfile` 适合静态文件到 socket；`mmap` 适合需要在用户态访问文件内容。

### 面试官追问

**追问 1：零拷贝一定更快吗？**  
**答：** 不一定。小数据、需要复杂业务处理或数据转换时，系统调用和映射管理成本可能抵消收益；`mmap` 还有缺页和地址空间管理成本。应针对数据规模和路径基准测试。

**追问 2：用户要修改文件内容后再发送，`sendfile` 还合适吗？**  
**答：** 若需要在用户态逐字节修改，就不能直接使用单纯的文件到 socket 路径。可考虑预处理、分段发送、协议头与文件内容组合，或其他 scatter-gather 接口，具体取决于修改方式。

## 45. `[S]` `fork`、`exec`、`waitpid` 分别做什么？什么是僵尸进程？

### 参考答案

`fork` 创建子进程，子进程初始拥有父进程地址空间的逻辑副本，通常通过写时复制避免立即复制全部物理页；返回值在父进程中是子 PID，在子进程中是 0。`exec` 不创建新进程，而是用新程序映像替换当前进程的代码、数据、堆栈等，成功时不会返回，PID 通常保持不变。

子进程退出后，内核保留其退出状态和少量统计信息，等待父进程通过 `wait/waitpid` 回收。在父进程尚未回收期间，子进程处于僵尸状态；僵尸不再运行，也基本不占用户内存，但持续占用 PID 和进程表项。父进程先退出的子进程称孤儿进程，会被系统中的 reaper 进程接管并最终回收。

`waitpid` 可等待指定子进程，并通过状态宏区分正常退出、信号终止等；配合 `WNOHANG` 可非阻塞查询。

### 答题要点

- `fork` 创建，`exec` 替换，`waitpid` 回收。
- 写时复制降低 `fork` 初始成本，但写大量内存仍昂贵。
- 僵尸已经退出，只是退出状态未被父进程回收。

### 面试官追问

**追问 1：多线程进程 `fork` 后子进程有哪些风险？**  
**答：** 子进程只保留调用 `fork` 的线程，但会继承互斥锁等内存状态；若锁原本由消失的其他线程持有，子进程再加锁可能永久阻塞。`fork` 到 `exec` 之间通常只调用 async-signal-safe 函数，或使用 `posix_spawn` 等更合适接口。

**追问 2：如何避免大量僵尸进程？**  
**答：** 父进程应及时调用 `waitpid`，可在事件循环中处理 `SIGCHLD` 后循环 `waitpid(-1, ..., WNOHANG)`，或使用其他进程监管机制。不能仅靠忽略进程列表中的僵尸。

## 46. `[S]` Linux 下如何限制、定位一个异常服务进程？

### 参考答案

限制方面，`setrlimit` 可设置进程资源软/硬限制，例如 `RLIMIT_CPU` 限制 CPU 时间，`RLIMIT_AS` 限制虚拟地址空间，`RLIMIT_NOFILE` 限制可打开 fd 数，`RLIMIT_CORE` 控制 core dump。它适合做基础保护，但不是完整沙箱：用户程序还可能滥用系统调用、文件、网络、子进程等，严格隔离还需要权限、namespace、cgroup、seccomp 等机制；若简历未写这些，不必主动展开。

排查方面先确认症状，再选工具：`top/htop` 看总体 CPU 和内存；`ps` 或 `pidstat` 看线程、CPU、I/O 和上下文切换；`ss` 看 socket 状态；`lsof` 看打开文件；`strace` 看系统调用阻塞或错误；`gdb/pstack` 看线程栈；`perf` 看 CPU 热点；`dmesg` 看 OOM、硬件和内核信息。高 CPU 不应先盲猜死循环，可先定位线程再抓栈或 profile；内存增长要区分 RSS、虚拟内存、缓存和真实泄漏。

### 答题要点

- `setrlimit` 是资源上限，不是完整安全隔离。
- 排查思路：先现象、再指标、再线程/系统调用/调用栈。
- 能把工具和问题对应，而不是只报命令名。

### 面试官追问

**追问 1：`SIGKILL` 和 `SIGSTOP` 能被捕获或忽略吗？**  
**答：** 不能。它们由内核直接执行终止或暂停语义，进程无法安装处理器、阻塞或忽略。其他信号也应注意信号处理函数只能安全调用有限的 async-signal-safe 接口。

**追问 2：`RLIMIT_CPU` 和墙上时间超时有什么区别？**  
**答：** `RLIMIT_CPU` 统计进程消耗的 CPU 时间，进程长时间阻塞或睡眠可能不增加该值；墙上时间是现实经过时间。在线判题通常同时需要 CPU 限制和外部计时器，防止程序一直阻塞却不超 CPU 配额。

# 五、Git（47-48）

## 47. `[A]` `merge` 和 `rebase` 有什么区别？什么时候不能随便 rebase？

### 参考答案

`merge` 把两个分支历史合并，必要时产生一个 merge commit，保留真实分叉结构，不改写已有提交。`rebase` 把当前分支的一组提交逐个重新应用到新的基点上，使历史更线性，但会生成新的提交对象和 commit hash，本质上是改写历史。

个人尚未共享的功能分支可在合并前 rebase 到最新主线，整理提交；已经推送并被他人基于其开发的公共历史不应随意 rebase 和强推，否则同一逻辑会出现两套提交，给协作带来冲突。团队规范优先于个人偏好。

### 答题要点

- merge 保留分叉，不改已有历史。
- rebase 线性但重写 commit。
- 不要改写他人已依赖的公共历史。

### 面试官追问

**追问 1：rebase 发生冲突时怎么处理？**  
**答：** 修改冲突文件并确认内容，`git add` 标记已解决，再执行 `git rebase --continue`；若判断方向错误可 `git rebase --abort` 回到开始前。应逐提交理解冲突，避免机械选择 ours/theirs。

**追问 2：为什么 rebase 后通常需要强推？**  
**答：** 远端已有旧提交，而 rebase 生成了不同 hash 的新历史，普通 push 不是 fast-forward。确需更新自己的远端分支时优先使用 `--force-with-lease`，它会检查远端是否出现未预期的新提交，比裸 `--force` 安全。

## 48. `[A]` `reset`、`revert` 和 `cherry-pick` 分别用于什么场景？

### 参考答案

`reset` 移动当前分支指针，并根据模式处理暂存区和工作区。`--soft` 只移动分支指针，改动保留在暂存区；默认 `--mixed` 还重置暂存区，但保留工作区；`--hard` 连工作区也重置，可能丢失未保存修改，使用前必须确认范围。

`revert` 不删除历史，而是创建一个新提交来反向抵消指定提交，适合撤销已经共享到公共分支的修改。`cherry-pick` 把指定提交的变更应用到当前分支，生成新提交，适合选择性移植修复，但大量使用可能造成重复历史和后续冲突。

### 答题要点

- `reset` 移动分支指针，可改变本地历史。
- `revert` 新增反向提交，适合公共历史。
- `cherry-pick` 选择性移植提交。
- `reset --hard` 是高风险操作。

### 面试官追问

**追问 1：误删了一个尚未被垃圾回收的 commit，如何找回？**  
**答：** 可用 `git reflog` 查找 HEAD 和分支引用移动记录，定位原 commit hash，再创建分支或 reset 到该提交。reflog 有保留期限，不能把它当永久备份。

**追问 2：Git 保存的是差异还是快照？**  
**答：** 概念模型上每个 commit 指向一棵文件树快照，并通过父提交形成历史；Git 会在存储层使用压缩和 delta 优化空间，但理解命令语义时应按快照模型思考。

# 六、MySQL 经典题（49-50）

## 49. `[S]` MySQL InnoDB 为什么使用 B+ 树索引？什么是聚簇索引、覆盖索引和最左前缀？

### 参考答案

B+ 树扇出大、树高低，一次节点读取可获得大量键，能减少磁盘或页缓存访问次数；内部节点主要存键和子指针，数据集中在叶子层，叶子节点按键有序并相互连接，既适合等值查找，也适合范围扫描。相比二叉树，它更适合页式存储；相比普通哈希索引，它支持顺序和范围查询。

InnoDB 的聚簇索引叶子节点保存整行数据，一张表只有一个聚簇组织顺序，通常以主键构建；二级索引叶子节点保存索引列和主键值，查到后可能再通过主键访问聚簇索引，这叫回表。若查询所需列都能从某个索引取得，就形成覆盖索引，可避免回表。

联合索引按列顺序排序，能否有效利用取决于最左前缀。以 `(a,b,c)` 为例，按 `a`，或 `a,b`，或 `a,b,c` 查询通常可连续定位；跳过 `a` 往往不能利用其有序前缀。遇到范围条件后，其右侧列通常难再用于继续缩小连续扫描区间，但具体还要结合优化器和版本能力分析。

### 答题要点

- B+ 树优势：低树高、页友好、有序叶子、范围查询。
- 聚簇索引叶子是整行；二级索引叶子通常带主键。
- 覆盖索引避免回表。
- 联合索引要说明最左前缀与范围条件。

### 面试官追问

**追问 1：为什么推荐较短、稳定、趋势递增的主键？**  
**答：** 二级索引叶子会保存主键，主键过长会放大所有二级索引；频繁修改主键代价高；近似递增主键通常减少随机页分裂和碎片。但还要权衡分布式生成、安全和业务语义，不能机械规定必须自增。

**追问 2：哪些写法可能使索引难以有效使用？**  
**答：** 常见情况包括对索引列做无法等价改写的函数或运算、隐式类型转换、联合索引跳过左侧列、以 `%` 开头的模糊匹配、选择性太差导致优化器判断全表扫描更便宜。最终应通过 `EXPLAIN` 和真实数据分布确认。

## 50. `[S]` MySQL 事务的 ACID、隔离级别和 MVCC 是什么？

### 参考答案

ACID 中，原子性表示事务要么全部成功、要么回滚，InnoDB 借助 undo log 等机制实现；一致性表示事务前后数据库满足约束和业务不变量，它是原子性、隔离性、持久性与正确业务逻辑共同作用的结果；隔离性约束并发事务相互影响；持久性表示提交结果在故障后可恢复，通常依赖 redo log、刷盘策略等。

SQL 标准隔离级别从低到高包括读未提交、读已提交、可重复读、串行化。读未提交可能脏读；读已提交避免脏读，但同一事务两次查询可能看到不同已提交结果；可重复读让一致性读通常基于稳定快照；串行化最强但并发度最低。InnoDB 默认通常是可重复读，但不能只靠名称推导全部锁行为。

MVCC 让读写尽量不互相阻塞。InnoDB 记录隐藏的事务信息和版本链，通过 undo 中的历史版本及 Read View 判断某版本对当前事务是否可见。普通一致性读主要走快照；`SELECT ... FOR UPDATE`、更新和删除属于当前读，需要读取最新可见记录并加相应锁。可重复读下为防止范围当前读出现幻影，InnoDB 还会使用记录锁、间隙锁和 next-key lock。

### 答题要点

- ACID 不要只背中文，要能对应日志与并发机制。
- 隔离级别对应脏读、不可重复读、幻读。
- MVCC 核心：版本链 + Read View。
- 快照读与当前读要区分。

### 面试官追问

**追问 1：可重复读是否意味着任何查询结果永远不变？**  
**答：** 不是。普通一致性读通常基于事务快照，但当前读会读取最新可见数据并加锁；本事务自己的修改也能被自己看到。隔离级别、查询类型和事务边界共同决定结果。

**追问 2：事务死锁如何处理？**  
**答：** 数据库检测到等待环后通常选择一个事务回滚，应用必须捕获错误并按幂等原则重试。预防上应让事务尽量短、按一致顺序访问表和行、使用合适索引缩小锁范围，并避免在事务中等待外部调用。

# 一两天冲刺安排

## 第一天：形成主干

- 上午：1-12 题，重点是对象模型、资源管理、智能指针、移动语义。
- 下午：14-24 题，重点是 STL、互斥、原子、条件变量、死锁和线程池。
- 晚上：27-36 题，重点是 TCP 状态、可靠性、epoll、LT/ET 和 Reactor。
- 睡前闭卷口述所有 `S` 题，只记录卡住的关键词，不反复抄答案。

## 第二天：补齐系统与模拟

- 上午：37-46 题，重点是虚拟内存、系统调用、fd、零拷贝、`fork/exec/waitpid`。
- 中午：49-50 两道 MySQL 经典题；47-48 Git 快速过一遍。
- 下午：让同学或 AI 随机抽 20 道 `S` 题，每题限时 90 秒；回答后继续追问。
- 面试前：只看自己口述失败的题，不再扩展 Redis、分布式等新战线。

# 面试回答模板

遇到任何八股题，可用下面的四步结构：

1. **定义和结论**：一句话直接回答它是什么、核心区别是什么。
2. **底层机制**：说明关键数据结构、状态或执行过程。
3. **适用场景**：解释什么时候用，以及为什么。
4. **边界与风险**：指出失效条件、性能代价或常见误区。

例如回答 epoll：

> epoll 是 Linux 的 I/O 多路复用机制，适合大量连接、少量活跃的服务。它把关注集合维护在内核，通过 `epoll_wait` 返回就绪事件，避免应用每轮扫描全部 fd。LT 会在条件持续满足时重复通知；ET 主要在状态变化时通知，因此 ET 必须配合非阻塞 fd 并读写到 `EAGAIN`。它在高并发连接场景通常比 select/poll 更合适，但并不意味着任何操作都绝对 O(1)，也不保证在小规模连接下更快。

# 最后提醒

- 简历写了“熟练掌握”，面试官默认你不仅会定义，还能回答至少一层原理追问。
- 不要把实现细节说成 C++ 标准保证，例如虚表具体布局、`vector` 固定两倍扩容。
- 不要把协议栈可靠等同于业务成功，也不要把引用计数线程安全等同于对象线程安全。
- 不会的源码细节可以承认边界，但主干概念、运行流程和常见故障必须说清楚。
