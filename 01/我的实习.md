# 我的实习

## 建议使用方法

1. 第一遍先只看题目，每道主问题用 60-90 秒回答，优先讲清业务背景、个人职责、迁移流程和验证结果。
2. 回答时始终区分“公司已有的成熟设计”和“自己完成的迁移适配”，不要把旧代码中的功能设计包装成从零原创。
3. 涉及合作平台 SDK 时，不必强行背诵或披露具体类名，但要能说明旧接口与新接口之间的语义映射、调用顺序和异常路径。
4. 复习时结合实际代码补充一两个最熟悉的函数或界面；若暂时记不清实现细节，就说明职责边界，不现场编造。

---

## 标签说明

- `[S]`：实习面试的主干题，涉及业务背景、个人贡献、核心迁移流程和简历中的关键工作，应该优先掌握。
- `[A]`：进阶题，侧重工具使用、工程风险、验证方法和对工作边界的理解。

---

## 实习回答通用结构

回答实习题时，可以采用下面的四步结构：

1. **背景与目标**：原系统是什么，为什么需要迁移到新平台。
2. **个人职责**：明确自己负责的模块、界面和 API 适配工作。
3. **实施过程**：按真实顺序说明如何理解旧代码、完成 Qt 迁移和平台接口替换。
4. **验证与边界**：说明如何对比验证，以及哪些是已有设计、哪些是自己的贡献。

---

## 真实性边界

- 公司已经提供成熟旧代码和功能设计；个人贡献主要是理解原有实现，并完成 MFC 到 Qt 的界面迁移及合作平台 API 适配。
- `APPLOAD`、`BLOCK` 等命令属于已有功能的跨平台迁移，不表述为自己从零设计了 CAD 命令或底层内核。
- 可以讲清选点、对象标识、模型插入等接口的职责和迁移思路，但不虚构广联达平台的具体 SDK 类名。
- 验证结果以旧平台、合作平台和 AutoCAD 的功能对比为主，不编造未做过的性能测试或量化指标。

# 一、北京中维数通 C++ 研发实习（1-6）

## 1. `[S]` 请介绍一下你在北京中维数通的实习背景和主要工作。

### 参考答案

我在北京中维数通担任 C++ 研发实习生。公司有一套自研工业 CAD 平台，其交互方式和二次开发模型参考了 AutoCAD。在与广联达合作的项目中，对方提供了目标平台及 SDK，我们需要把公司已有的一部分成熟 CAD 功能迁移到该平台。这个任务并不是重新开发 CAD 内核，而是让已有功能在新的界面框架和平台接口下保持一致的业务行为。

我的主要工作是先阅读公司提供的旧代码，理解界面、业务流程和 CAD API 之间的调用关系，再完成 MFC 到 Qt 的界面迁移以及广联达平台 API 的适配。我独立负责过参数配置模块的迁移，涉及组合设备参数、管嘴工程参数和几何参数等界面，也参与了 `APPLOAD`、`BLOCK` 等命令，以及图形预览、对象标识读取和模型插入相关功能的迁移。完成后，我会通过旧平台、合作平台和 AutoCAD 的实际行为对比来验证结果。

### 答题要点

- 业务背景：把公司自研 CAD 平台上的成熟功能迁移到广联达提供的平台。
- 个人职责：理解旧代码，完成 MFC 到 Qt 的 UI 迁移和平台 API 适配。
- 主要内容：参数配置模块、`APPLOAD`、`BLOCK`、图形预览和模型相关接口。
- 职责边界：不是从零设计 CAD 功能，而是负责跨框架、跨平台迁移并保证行为一致。

### 面试官追问

**追问 1：既然已有旧代码，你在其中的价值主要体现在哪里？**  
**答：** 旧代码提供的是功能基线，但不能直接在新平台运行。我需要先还原它的真实调用链，识别 MFC、旧平台 API 与通用业务逻辑的边界，再把界面事件、数据传递和 CAD 操作映射到 Qt 与新 SDK。迁移完成后还要排查交互、显示和数据同步问题，因此工作重点是理解、适配和验证，而不是简单复制代码。

**追问 2：为什么这类迁移不能只做接口名称替换？**  
**答：** 两个平台在界面事件、对象生命周期、选点交互、对象标识和错误返回方式上都可能不同，即使两个接口名字相似，调用前提和结果语义也未必一致。只有先确认旧功能的输入、状态变化和预期输出，再做语义层面的映射，才能避免“可以编译但行为不一致”的问题。

## 2. `[S]` 你是怎样把一套成熟的 MFC CAD 功能迁移到 Qt 和新平台 SDK 上的？

### 参考答案

我一般先把旧实现按职责拆开理解：第一层是 MFC 控件、消息响应和窗口状态；第二层是参数校验、命令流程等业务逻辑；第三层是选点、对象读取、图形创建或模型插入等旧平台 API。迁移时，能够保持不变的业务规则继续沿用，界面层改成 Qt 控件和信号槽，平台相关调用则根据新 SDK 的语义重新适配，而不是对旧代码逐行翻译。

具体实施时，我会选择一条最小可运行链路，先让界面输入能够触发业务流程，再接通关键 CAD API，最后补齐取消、失败和状态回显等路径。每完成一个模块或命令，就使用相同输入分别在旧平台、合作平台和 AutoCAD 中执行，比较界面状态、图形结果和操作习惯。这样可以尽早判断问题属于 Qt 界面、业务数据，还是平台接口适配。

### 答题要点

- 先分层理解旧代码：界面层、业务流程层和平台 API 层。
- 迁移原则：保留稳定业务规则，重写框架相关代码，按语义映射平台接口。
- 实施顺序：先打通最小链路，再补齐失败、取消和状态更新等分支。
- 验证方式：用相同输入对比旧平台、合作平台和 AutoCAD 的行为。

### 面试官追问

**追问 1：你如何判断一段旧代码可以复用还是必须重写？**  
**答：** 如果代码只是参数校验、数据转换或与平台无关的业务规则，通常可以在确认依赖后复用；如果它依赖 MFC 控件、窗口句柄、消息机制，或者直接操作旧 CAD 平台对象，就需要迁移或重新适配。我会先看它依赖的类型和生命周期，而不是只根据函数名判断。

**追问 2：如果新旧平台没有一一对应的 API，你会怎么处理？**  
**答：** 我会先确定旧接口最终要实现的业务语义，再看新平台能否通过多个基础接口组合完成；必要时在业务代码与 SDK 之间增加一层小范围转换，统一参数、返回值和错误处理。如果确实存在能力差异，我会记录差异并与负责人确认，而不是为了表面一致去编造调用。

## 3. `[S]` 请具体讲一下 `APPLOAD` 命令的迁移过程。

### 参考答案

`APPLOAD` 的功能和原始流程在公司旧代码中已经实现，我负责的是把这条流程迁移到 Qt 和合作平台。开始时，我先沿着旧代码梳理命令入口、文件选择、输入校验、平台加载调用和结果反馈之间的关系，确认哪些逻辑属于原有业务规则，哪些部分直接依赖 MFC 或旧平台。之后用 Qt 控件和信号槽重建交互，并将实际加载动作替换为合作平台提供的对应能力。

迁移时我关注的不只是正常加载成功，还包括用户取消、路径或文件不符合要求、平台调用失败以及界面反馈是否正确。对于旧代码里已经存在的校验和提示，我尽量保持行为一致；对于两套 SDK 返回值和错误表达不同的地方，则在适配位置统一转换。最终通过在旧平台和新平台上执行相同操作，检查命令是否可触发、加载结果是否正确、失败路径是否有合理反馈。

### 答题要点

- 原功能已有：先梳理旧代码的命令入口、校验、加载和反馈链路。
- UI 迁移：把 MFC 界面事件改为 Qt 控件与信号槽。
- API 适配：根据新 SDK 的能力替换平台加载调用，并统一结果表达。
- 验证重点：成功、取消、非法输入和加载失败等路径的行为一致性。

### 面试官追问

**追问 1：`APPLOAD` 迁移中最容易遗漏什么？**  
**答：** 最容易只验证“正常选择一个文件并加载成功”，却漏掉取消选择、路径编码、重复操作、文件类型校验和 SDK 失败返回等分支。我的处理思路是以旧实现的完整行为为基线，把每个出口都列出来，再逐项确认 Qt 界面是否收到了正确状态。

**追问 2：你怎样避免平台 SDK 调用散落在 Qt 界面代码中？**  
**答：** 界面槽函数主要负责读取输入和更新显示，真正的平台调用集中在明确的业务或适配函数中，由它完成参数转换、调用 SDK 并返回统一结果。这样即使平台接口发生变化，修改范围也相对集中，同时更容易单独定位是 UI 问题还是加载调用问题。

## 4. `[S]` `BLOCK` 命令和 CAD 交互接口是怎样迁移的？

### 参考答案

`BLOCK` 的核心语义是根据块名、基点和选中的图元创建可复用的块定义。这个功能同样已有成熟旧实现，我负责迁移相关 Qt 界面和平台接口。迁移时，我先确认界面输入如何进入命令流程，再依次处理实体选择、三维基点获取、对象标识读取和块创建等环节；每个环节都根据合作平台 SDK 的输入输出重新做映射，不直接复用旧平台的对象类型。图形预览和模型插入是我参与的其他 CAD 二次开发适配工作，并不把它们等同为 `BLOCK` 命令本身。

选点是一个比较直观的例子：用户点击“捕捉点”按钮后，需要进入 CAD 场景选择三维点。旧平台和合作平台调用的 API 不同，但界面真正需要的是“成功得到一个点”或“用户取消”这样的业务结果，因此我把平台返回结果转换后再更新 Qt 界面状态。完成迁移后，我会使用相同的图元、块名和基点在不同平台执行，比较块定义、基点、所选对象的处理结果和图形显示是否符合预期。

### 答题要点

- 命令语义：根据名称、基点和所选图元创建块，而不是只迁移一个对话框。
- 核心链路：界面输入、实体选择、三维选点、对象标识和块创建。
- 适配原则：平台对象不跨 SDK 直接复用，只传递业务层真正需要的结果。
- 结果验证：对比块定义、基点、所选对象的处理结果和最终图形显示。

### 面试官追问

**追问 1：为什么对象标识读取在跨平台迁移中需要特别注意？**  
**答：** 对象标识通常依赖当前文档、数据库和对象生命周期，不同 SDK 的类型、有效范围和打开方式可能不同。迁移时不能把旧平台的标识值当成新平台对象直接使用，而要通过新平台的选择或查询结果取得有效标识，并在正确的文档上下文中完成后续操作。

**追问 2：如果选点时用户取消了，你会怎样处理？**  
**答：** 取消应该作为一种正常业务结果返回，而不是当作成功点或异常崩溃处理。界面不更新基点值，后续依赖该点的创建流程也不能继续，同时要恢复到用户可以再次操作的状态。验证时我会分别覆盖成功选点和主动取消两条路径。

## 5. `[S]` MFC 到 Qt 的迁移中遇到过哪些兼容问题，你是怎样定位和验证的？

### 参考答案

旧客户端以 MFC 为主，迁移到 Qt 后，窗口父子关系、消息与事件机制、控件布局和对象生命周期都发生了变化。我处理过 Qt 与 MFC 混合嵌入场景中的子窗口创建、切换页面白屏、控件尺寸不随窗口更新等问题，也排查过界面显示与底层参数不同步的问题。这些问题表面上都表现为“界面不对”，但根因可能分别位于窗口生命周期、布局刷新、信号槽连接或 CAD 数据读取环节。

我的排查方式是先稳定复现，再用日志记录关键函数的进入、返回值和状态变化，用断点观察窗口创建、切页及数据更新顺序，同时对照旧代码确认预期行为。定位时会把 UI 状态和业务数据分开检查：先确认对象标识、参数或模型数据是否正确，再判断是否只是显示刷新问题。修复后除了复测原场景，我还会在旧平台和 AutoCAD 中执行同样操作进行对比，并通过 Git 分支和小步提交控制修改范围。

### 答题要点

- 典型问题：子窗口创建、切页白屏、控件尺寸异常和界面数据不同步。
- 定位手段：稳定复现、日志、断点以及新旧代码调用顺序对比。
- 分层判断：分别检查窗口生命周期、Qt 事件、业务数据和 CAD 对象状态。
- 回归验证：复测故障路径，并与旧平台、AutoCAD 的行为进行比较。

### 面试官追问

**追问 1：遇到切换页面白屏时，你会优先检查什么？**  
**答：** 我会先确认页面对象是否已经创建、父子关系是否有效，以及切换前后的可见状态和尺寸是否正确；随后检查切页信号是否进入了预期槽函数、数据初始化是否提前返回。这样可以先区分“窗口根本没有正确显示”和“页面显示了但数据或绘制没有完成”。

**追问 2：如何判断是 Qt 显示问题还是底层 CAD 数据问题？**  
**答：** 我会在更新界面前检查业务层拿到的参数、对象标识和操作返回值。如果数据正确但控件没有刷新，重点排查信号槽、布局和显示生命周期；如果数据本身已经错误，则继续向前追踪平台 API 和数据同步流程。分层检查比直接在界面代码里反复修改更容易定位根因。

## 6. `[A]` 你在实习中如何使用 Codex 提高迁移效率，又怎样保证结果可靠？

### 参考答案

我把 Codex 主要当作代码理解和迁移辅助工具，而不是让它替我决定最终实现。面对公司已有的成熟项目时，我会给出范围明确的相关代码或接口信息，让它帮助梳理调用链、查找相似实现、总结 MFC 控件与 Qt 信号槽之间的对应关系，或者先生成一份平台适配的代码骨架和检查清单。这样可以减少在大型旧项目中重复查找和整理的时间，但具体接口选择、对象生命周期和集成方式仍由我结合项目代码判断。

对 Codex 给出的内容，我会先检查修改范围和接口依据，再通过编译、日志、断点和功能测试验证，不能因为代码看起来合理就直接合入。尤其是 CAD SDK 可能存在版本差异或私有接口，AI 容易生成不存在的 API，因此必须以实际头文件、项目中的既有用法和运行结果为准。最终仍会把新平台结果与公司旧平台、AutoCAD 进行对比；涉及公司代码时，也只在公司允许的环境和范围内使用工具。

### 答题要点

- 使用场景：阅读旧项目、梳理调用链、查找参考实现和生成迁移骨架。
- 人的职责：确认接口语义、对象生命周期、修改范围和最终技术方案。
- 验证闭环：代码审查、编译、日志、断点、功能测试和跨平台对比。
- 风险控制：防止虚构 API、忽略版本差异，并遵守公司代码保密要求。

### 面试官追问

**追问 1：能举一个 Codex 真正提高效率的例子吗？**  
**答：** 在迁移一个已有功能前，我可以让它先根据相关旧代码整理“界面事件—业务函数—平台调用”的链路，并列出需要替换的 MFC 控件、信号槽和旧 SDK 接口。这样我能更快找到项目中的相似实现并搭好初始迁移框架，再把时间集中在平台差异、调试和验证上。

**追问 2：如果 Codex 生成了一个项目中不存在的 SDK 接口，你会怎么办？**  
**答：** 我不会通过猜测继续补代码，而是回到实际 SDK 头文件、文档和仓库中的调用示例核对能力边界，再用真实接口改写。如果新平台没有直接对应能力，就按业务语义组合已有接口，或者向负责人确认差异。AI 输出只能作为待验证的候选方案，不能作为接口存在的证据。
